# Changelog

## v0.8.0

**In short:** the Python package no longer depends on PyArrow: reads return `carquet.Table` (Arrow C Data arrays, PyCapsule interface) and the features PyArrow supplied (exact row filters, `ARROW:schema` restore and write, type handling on write) moved into the C library, where an `ArrowArrayStream` scan with row groups, row windows and DNF predicates serves C users too. Real-world files (nullable, dictionary-encoded and string columns, reads without mmap) are several times faster to read and write; 11 bugs that returned wrong results or wrote corrupt files without an error are fixed, plus 7 memory-safety fixes for crafted input and a compatibility pass against pyarrow, DuckDB, polars, fastparquet and apache/parquet-testing (`DECIMAL(p, 0)` readable everywhere, UTF-8 safe truncated statistics, legacy list layouts); zlib moves to 1.4. ABI: additions only (new functions and structs, `CARQUET_FILTER_NOT_IN` appended to the filter enum), but the Arrow export now types DECIMAL and INT96 as pyarrow does (see Breaking changes). Default output bytes change for dictionary chunks larger than one page (now cut into several pages) and in the cases listed under Performance; REQUIRED non-dictionary columns are written as before.

### Breaking changes

- **Python: no PyArrow** ([the package now has no dependencies](python/README.md)): `read_table`, `ParquetFile.read` / `read_row_group(s)` / `slice` / `head` return a `carquet.Table` and `iter_batches` yields `carquet.RecordBatch` (Arrow C Data arrays held by the C library, reference-counted views; `to_pylist()` / `to_pydict()` / `to_numpy()` / `to_pandas()` / `to_polars()` / `to_pyarrow()`, and the Arrow PyCapsule interface for polars, DuckDB, PyArrow, nanoarrow...). `pf.schema` / `read_schema()` return a `carquet.Schema`. `filters` takes the DNF form only (no `pyarrow.compute.Expression`); the `arrow` extra is replaced by `pandas`. `ParquetWriter` no longer casts: narrower integers into int64 and float32 into float64 are widened in C, other type differences are errors.

- **Arrow export types follow `pyarrow.parquet`**: `carquet_arrow_export_batch()`, `carquet_reader_read_arrow()` / `carquet_reader_read_arrow_fields()` and `carquet_arrow_export_schema()` now export `DECIMAL` as `decimal128` (precision up to 38) or `decimal256` (up to 76), whatever its physical type (INT32, INT64, FIXED_LEN_BYTE_ARRAY, BYTE_ARRAY), and `INT96` as `timestamp[ns]`, instead of their storage (`i`, `l`, `w:N`, `z`, `w:12`). A BYTE_ARRAY decimal value wider than its Arrow type fails the export with `CARQUET_ERROR_DECODE`; an FLBA decimal wider than 16 / 32 bytes keeps its storage type. Arrow-written decimals now round-trip through carquet (`write_arrow` then `read_arrow`) as decimals. The two exporters share one Parquet -> Arrow leaf mapping (`src/reader/arrow_leaf.c`) instead of two copies.

### Features

- **Arrow C Stream export with row selection**: `carquet_reader_export_arrow_stream()` (+ `carquet_arrow_stream_options_t`) hands a file to any `ArrowArrayStream` consumer: a selection of top-level fields, `row_groups` in any order, a row window (`row_offset` / `row_limit`), a `predicate` and `restore_arrow_schema`. Primitive and single-level LIST / MAP selections go through the batch reader (parallel decode); STRUCT and deeper nesting through `read_arrow_fields`, one row group per batch. Test: `tests/test_arrow_stream.c`.
- **Exact row predicates in C** (`carquet_predicate_t`, `src/reader/arrow_filter.c`): a DNF of `carquet_filter_clause_t` (new op `CARQUET_FILTER_NOT_IN`) on any leaf column outside a LIST / MAP, struct fields included. Row groups are pruned with statistics (`carquet_reader_predicate_row_groups()` exposes it), pages with the page index for a single conjunction, then every batch is filtered exactly on its Arrow values (DECIMAL numerically, INT96 by instant, unsigned unsigned, IEEE floats with PyArrow's NaN semantics) and compacted (`carquet_arrow_take`).
- **`ARROW:schema` restore in C** (`src/reader/arrow_restore.c`, the FlatBuffer reader shared in `fb_read.h`): the stored Arrow types come back as `pyarrow.parquet` gives them: time zones, `large_*` and view types, dictionaries (encoded by hashing), durations, the null type, fixed-size lists (all-null children for null lists), decimal widths, struct child names, field and schema metadata. The footer key/value metadata is always the schema metadata.
- **`ARROW:schema` written from an Arrow schema**: `carquet_writer_set_arrow_schema()` stores the IPC form of the data's own Arrow schema (every type with an IPC form, dictionaries, nullability, metadata) and its key/value metadata.
- **Arrow import**: durations (INT64), string / binary views (BYTE_ARRAY), the null type (INT32 annotated Null, exported back as Arrow null); narrower integers into INT64 columns and float into DOUBLE columns are widened; a null in a non-nullable field is refused (it used to write the slot's leftover value).
- **Bindings support** (`src/reader/arrow_ref.c`): `carquet_arrow_ref_*` (a refcounted owner of an exported array; `export`, `export_child`, `export_select` give independent views, sliced, from any thread), `carquet_arrow_schema_copy` / `copy_child` / `select` / `build`, `carquet_arrow_array_build`, `carquet_arrow_stream_from_arrays`, and C PyCapsule destructors (`carquet_arrow_capsule_init` + `carquet_arrow_*_capsule_destructor`) so capsules never run interpreter code while being destroyed.
- **Python**: `carquet.Table` / `RecordBatch` / `ChunkedArray` / `Array` / `Schema` / `Field` / `DataType` (`carquet/arrow.py`, values read in place by `carquet/_decode.py`); `carquet.table()` imports any PyCapsule producer, dict or DataFrame; writing takes Arrow producers, dicts of Python values / NumPy arrays / pandas Series and DataFrames (`carquet/_build.py`, PyArrow's type mapping and `pandas` metadata). `ParquetFile.arrow_stream(columns, filters=, row_groups=, batch_size=)` and `__arrow_c_stream__`. Exact filters (inexact literals such as `x < 2.5` on an integer column are rewritten on the neighbouring representable values). Tests: `python/tests/test_core.py` (also run with PyArrow unimportable by `test_no_pyarrow.py`), `test_stream.py`; the other modules keep PyArrow as an oracle.
- **Python documentation**: every public function, class, method and property has a docstring (80 had none), so `help(carquet)`, `help(carquet.read_table)`, `help(carquet.Table)`... are a complete reference, kept so by a test. [`python/README.md`](python/README.md) is the package documentation only (contents, a table of common tasks, reference), without change notes; wheel packaging and the development loop moved to [`python/BUILDING.md`](python/BUILDING.md). The Python sections of the main README, its translations and the website describe the dependency-free package.
- **Fuzzing**: `fuzz/fuzz_arrow_stream.c` (stream with restore, predicate and ref views over arbitrary files); `fuzz_arrow_schema` also drives the full IPC Schema decoder. `fuzz_arrow_stream` checks every batch against the stream's schema the way a consumer reads it (layout per format, buffer extents, offsets, dictionary codes). libFuzzer builds now compile libcarquet itself with ASan / UBSan (only the harness was, so a use-after-free inside the library went unnoticed).
- **polars in the benchmark**: `run_benchmark.py --polars` (opt-in, needs `polars`) runs `benchmark/benchmark_polars.py`, polars' own Rust reader / writer (not PyArrow), with the same data, row group size, zstd level, statistics and LZ4_RAW for `lz4`; polars cannot write BYTE_STREAM_SPLIT or page checksums and dictionary-encodes `id` and `category` on its own. `plot_readme_chart.py` draws it as a fifth library. README results re-measured with carquet 0.8.0 (Apple M3, 2026-11-09, `benchmark/bench_0.8.0_darwin_arm64_20261109.json`): at 10M rows polars writes faster (38–49 ms vs 49–61 ms; its dictionary-encoded files are 15–45% smaller except with zstd; carquet with the same two dictionary columns writes in 45–51 ms), carquet reads 2.0–3.0x faster with a codec, and 2.0–4.1x faster on the same file.

### API

- `carquet_schema_node_geospatial_crs()` returns a GEOMETRY or GEOGRAPHY node's CRS whole (`""` when the type gives none, `NULL` for other nodes). The logical type's fixed `crs` array still holds at most 127 bytes. The Python binding uses it when present. ABI-compatible: no public struct changes.

### Bug Fixes

Wrong results without an error (one test per fix in `tests/test_fixes_0_7_4.c` unless noted, each failing on the 0.7.3 sources):
- **Shifted values after a skip**: on an OPTIONAL column, the dense-value cursor kept from one page was reused on the next one when a read resumed at the same in-page position, so `read 300 → carquet_column_skip(1000) → read` returned the values of rows 1000.. instead of 1300.. (also hit by the batch reader with a page filter when columns have different page boundaries). The cursor is invalidated on every page change (`page_reader.c`).
- **Rows dropped by the page filter on LIST / MAP columns**: a page or row group was treated as all-null when `null_count >= rows`, but for a repeated leaf `null_count` counts level slots, not rows (`[5, null, null, null]` is 3 nulls in 1 row), so EQ / IN / ranges / `IS_NOT_NULL` could prune the whole row group. The shortcut is disabled for repeated leaves (`page_filter.c`).
- **Rows dropped by a ColumnIndex with lists of different lengths**: the page count was clamped to the shortest list, including the optional `null_counts`, and the filter then scanned only `min(ColumnIndex, OffsetIndex)` pages. A short `null_counts` is now ignored, a ColumnIndex whose required lists (`null_pages`, `min_values`, `max_values`) are missing or disagree is rejected, and a ColumnIndex that does not match the OffsetIndex page count keeps every page (`page_index.c`, `page_filter.c`).
- **Bloom pruning of ±0.0**: the bloom filter hashes the stored bits while min/max compare numerically, so EQ / IN `+0.0` pruned a row group holding `-0.0` (and the reverse). A zero probe now checks both signs for FLOAT, DOUBLE and FLOAT16.
- **`preserve_dictionaries` returned PLAIN values as dictionary indices** ([#45](https://github.com/Vitruves/carquet/issues/45), fix and test from [#46](https://github.com/Vitruves/carquet/pull/46) by @xmaton): when a dictionary chunk fell back to PLAIN pages part way through (parquet-mr, Arrow C++ and DuckDB do once the dictionary is full), a REQUIRED fixed-width column viewed the PLAIN page directly and handed its bytes out as `uint32_t` indices, far outside the dictionary, without an error. `page_values_can_be_viewed_directly()` now leaves such pages to the decode path, which rejects them with `CARQUET_ERROR_INVALID_ENCODING` (`page_reader.c`). Test: `tests/test_dictionary_fallback.c` (splices a dictionary chunk and a PLAIN chunk into one).
- **Deprecated statistics on unsigned columns**: the pre-1.10 parquet-mr `min` / `max` fields (signed order) were trusted for `UINT_8..UINT_64` / unsigned INTEGER columns, which sort unsigned, so a column holding `1` and `0x80000000` could be pruned for EQ 1. They are now only used for signed sort orders (`statistics.c`).
- **A GEOMETRY or GEOGRAPHY CRS longer than 127 bytes was cut** to its first 127 when a file was read, with no sign it had been cut: inline PROJJSON, which DuckDB writes and parquet-testing's `geospatial/crs-arbitrary-value.parquet` carries (2,316 bytes), came back as a different, unparseable CRS. The footer parser now also keeps the whole CRS in the schema element, `carquet_schema_node_geospatial_crs()` returns it, and the writer writes it back when given a schema read from a file (deep-copied, so the reader may close first). Test: `long_geospatial_crs` in `tests/test_fuzz_regressions.c`. Output bytes unchanged except that such a CRS is no longer truncated on rewrite.

Corrupt output:
- **Append left a stale footer**: `carquet_writer_open_append()` writes the new row groups and footer over the old footer without truncating the file; when the rewritten tail was shorter (an empty-string minimum or encoding stats are not restored byte for byte), the old footer length and `PAR1` stayed at the end and the file could not be opened ("Truncated binary data"). The file is truncated after the footer (new `carquet_ftruncate64()` in `core/compat.h`, `_chsize_s` on Windows).
- **Schema elements out of depth-first order**: elements are serialised in insertion order, so adding a child to a group after a sibling group (`add a, add b, add x under a`) wrote a schema that read back as `a.b.x`, contradicting the column paths. Adding to such a closed group now fails (`CARQUET_ERROR_INVALID_ARGUMENT` from `carquet_schema_add_column()`, `-1` from `carquet_schema_add_group()` and the list / map / variant helpers); building in depth-first order, the only order that produced valid files, is unchanged.
- **GeospatialStatistics accumulated across row groups** ([#41](https://github.com/Vitruves/carquet/issues/41), reported with a fix in [#42](https://github.com/Vitruves/carquet/pull/42) by @pedrobtz): the bounding box and geometry types of each GEOMETRY / GEOGRAPHY chunk included every earlier row group. They are reset per row group (`column_writer.c`, `row_group_writer.c`).
- **RLE encoder hid allocation failures**: the encoder ignored failed buffer appends and returned `CARQUET_OK` with a truncated stream, so an out-of-memory condition wrote a corrupt page instead of failing. The first failure is now kept and returned by `put` / `flush` (`rle.c`).
- **`max_rows_per_page` ignored within one `write_batch` call**: the row cap was only checked between write chunks, and fixed-width columns are chunked by `page_size` (at least 1024 values), so 3000 rows written in one call with a cap of 1000 became a single page. Chunks now stop at the cap, on the serial path and in the page-parallel planner (which stay byte-identical). Files written with `max_rows_per_page` and large batches now have more, smaller pages.

Memory safety (crafted or invalid input):
- A LogicalType union with two members set (e.g. DECIMAL then TIMESTAMP) kept the first member's bytes in the second's parameters, so `is_adjusted_to_utc` could hold a byte that is not a valid `bool` (undefined behaviour; found by the libFuzzer build once libcarquet itself was sanitized). Each member now starts from zeroed parameters (`parquet_types.c`).
- `carquet_writer_write_arrow()`: a null dictionary slot on a non-nullable field kept a "present" level without a value, so levels and values disagreed (heap over-read in the column writer, garbage pointers for BYTE_ARRAY). It is now rejected with `CARQUET_ERROR_INVALID_ARGUMENT` (`arrow_c_import.c`).
- `write_arrow_schema`: a struct with more than 64 fields overflowed a 64-entry stack array while building the `ARROW:schema` footer entry; the child list is now sized from the schema (`arrow_schema.c`).
- `preserve_dictionaries`: dictionary indices were decoded straight into the caller's buffer without the `index < dictionary_count` check of the materializing path, so a crafted file made callers index past their dictionary. V1 and V2 pages now reject out-of-range indices (`page_reader.c`).
- A stored fixed-size list size is no longer a licence to allocate: 3 null lists with a size of 2^30 in a 501-byte file asked for 25 GB. Child slots made up for empty null lists are capped at 2^27 per batch (`CARQUET_ERROR_DECODE` beyond). Found by `fuzz_arrow_stream`.
- A footer with a negative row count (file or row group) produced an Arrow batch of negative length; the footer is now rejected with `CARQUET_ERROR_INVALID_METADATA` when it is parsed (`parquet_types.c`). Found by `fuzz_arrow_stream`.
- `carquet head -n <huge> --filter`: the row count was not capped before the filtered path sized its output (`limit * columns` wrapped, then a heap overflow). The count is capped to the file's rows and the allocation is overflow-checked.

Arrow stream and `ARROW:schema` restore (new in this release; one test per fix in `tests/test_fixes_0_8_0.c`):
- **Dictionary restore handed out plain values as a dictionary**: when a batch held more distinct values than the stored index type can count (`dictionary<int8, string>` with 300 values), the batch kept its string array under a schema announcing int8 indices and a dictionary. The read now fails with `CARQUET_ERROR_DECODE`, as pyarrow does (`arrow_restore.c`).
- **Row windows on nested files could not be imported by Arrow C++ / PyArrow**: on the row-group path the window was an offset on the batch itself ("struct has non-zero offset, cannot be imported as RecordBatch"). It is now carried by the fields; the batch offset is always 0 (`arrow_c_stream.c`).
- **`ARROW:schema` trusted too far**: a decimal width its precision cannot have (`decimal32` with 38 digits) cut values to 4 bytes; the null type over a column holding values dropped them. The first keeps the exported type, the second fails with `CARQUET_ERROR_DECODE` (`arrow_restore.c`).
- **Fixed-size list restore**: lists are served from the list's own child without a copy when no null list is stored empty (it used to allocate 8 bytes per element and copy every value).
- `carquet_predicate_t`: RANGE on a FIXED_LEN_BYTE_ARRAY column requires `lo_size` / `hi_size` equal to the type length at compile time (it was refused later, only on files with a page index); a clause's unused members are no longer read.
- The stream's schema leaked one node per dictionary-restored field (`release_schema` in `arrow_c_read.c` ignored `dictionary`).

Windows:
- **Reads without mmap could return bytes from the wrong place**: a positional read on Windows moves the handle's file pointer, and the reader still loaded the page-index / bloom data, the prebuffer and the header magic with `fseek` + `fread` on the same stream, so a filtered read (page index + pages read in parallel) could decode the wrong bytes (`test_batch_pipeline`: `strings_required_filtered_pread` returned a wrong row count on every Windows build). A reader with positional I/O now does every read positionally (`file_reader.c`). New in this release with the non-mmap pipeline; POSIX `pread` never moved the position.

Python (tests in `python/tests/test_core.py`):
- `carquet.table({...})` / `write_table({...})` with Arrow arrays as columns: a list, struct or dictionary array kept the producer's field name (usually empty) instead of the dict key, and an array whose schema carries metadata failed with a ctypes `ArgumentError`. The column's schema node is now rebuilt under the dict key, children and dictionary moved (`_build.py`).
- `to_pylist()` / `to_pandas()` looked up the dictionary index (and read the string view) of null slots, whose content Arrow leaves unspecified: an out-of-range index under a null raised `IndexError` / `KeyError` on data from other producers. Null slots are skipped (`_decode.py`).
- `to_pandas()` no longer reads the `future.infer_string` option on pandas 3, where it is deprecated (`Pandas4Warning`).
- `to_numpy()` on a date32 column read 8 bytes per value from a 4-byte buffer (wrong dates, out-of-bounds read). `to_pandas()` now returns `datetime.date` objects for dates, keeps the timestamp unit on pandas >= 2 and returns list cells as ndarrays, as PyArrow does. Time-zone aware pandas columns are written in their own unit (they became `timestamp[ns]`); the pandas metadata carries decimal precision / scale and the `str` column-index dtype. `Statistics.min` of an empty-string minimum is `""` instead of `None`.

Compatibility:
- A V2 data page whose data section is 0 bytes with `is_compressed` set (all-null pages from parquet-java) was handed to the codec, and GZIP / BROTLI reject an empty input, so the file could not be read. An empty section is no longer decompressed (same as Arrow, GH-31992).
- **`DECIMAL(p, 0)` columns could not be read by DuckDB, polars or fastparquet**: the schema element carried `precision` without `scale` when the scale was 0 ("DECIMAL requires a length and scale specifier"). Both are now always written (`parquet_types.c`).
- **Truncated STRING statistics stay valid UTF-8**: a min / max longer than `max_statistics_size` was cut at a byte and the max byte-incremented, which could leave an invalid sequence (pyarrow raised `UnicodeDecodeError` on `statistics.max`). STRING / JSON / ENUM bounds are cut on a character boundary and the last code point is incremented, as parquet-java and arrow-rs do; the max is dropped when no such bound exists. BYTE_ARRAY columns are unchanged.
- **Legacy list layouts are read**: repeated fields outside a LIST group, LIST groups whose repeated node is the element (a repeated primitive, a group with several fields, with one repeated field, or named `array` / `<list>_tuple`) and MAP groups without a value column failed in `carquet_reader_read_arrow()` / the Arrow stream ("failed to assemble field"). They follow the format's backward-compatibility rules and come out typed as Arrow C++ types them (parquet-testing `old_list_structure`, `repeated_no_annotation`, `repeated_primitive_no_list`, `map_no_value`).
- **Required fields of a null struct**: a REQUIRED leaf under a null OPTIONAL group was exported with nulls in a non-nullable Arrow field, which `pyarrow.parquet.write_table` refuses. Such fields no longer carry a validity bitmap.
- **Dictionary page with no `encodings` listed**: a chunk from old parquet-mr with an empty `encodings` list and no `dictionary_page_offset` failed with "Expected data page" (parquet-testing `nation.dict-malformed.parquet`); the first page is now probed in that case too.
- **Arrow `arrow.uuid` / `arrow.json` fields are written with the UUID / JSON logical type** (they were plain `FIXED_LEN_BYTE_ARRAY(16)` / STRING for readers that ignore `ARROW:schema`, e.g. DuckDB).
- `carquet_arrow_ref_export()` of a whole batch that itself carries an offset now moves it into the children (PyArrow refuses a record batch with a top-level offset).
- Tests: `tests/test_compat_0_8_0.c`, `python/tests/test_compat.py`. Checked in both directions against pyarrow 26, DuckDB 2.0, polars 2.1 and fastparquet 2026.9 (302 files written by carquet across codecs, encodings, page versions and types; 504 files written by them, read through every Python entry point and the CLI) and on the 243 files of apache/parquet-testing (226 identical to pyarrow, no crash; known gap: data pages with `num_values = 0`, `empty_data_pages_v1/v2.parquet`, are rejected).

CLI:
- `head`, `tail`, `sample`, `cat` and `export` read level slots as rows: a LIST / MAP column printed one element per row, misaligned with the other columns, and `tail` / `cat --offset` started at the wrong row (`carquet_column_skip()` skips slots). All of them now go through one row cursor (`commands.c`) that groups slots into rows and prints a repeated column as one list per row (`[1, null, 3]`, `[]`, `null`); rows of a row group whose column cannot be read print `?` instead of shifting the next row group (the old `tail` miscount). `head --filter` / `cat --filter` print single-level list columns the same way (they were empty before) and `head --filter` shows nulls as `null` like `head`. Tests in `tests/test_cli_format.c`.

- `CARQUET_ERROR_INIT` used designated initializers, which C++ only accepts from C++20: C++17 consumers failed to build on MSVC, and Clang / GCC warned under `-Wpedantic`. It is now a positional initializer with the same values, valid C and C++ (checked from C++11 to C++20 with `-Wpedantic -Werror`).

### Dependencies

- **zlib 1.4** ([#40](https://github.com/Vitruves/carquet/issues/40)): the zlib that CMake fetches (no system zlib, or `CARQUET_BUNDLE_DEPS=ON`, as in the release archives and the Python wheels) and that xmake builds moves from 1.3.1 to 1.4, which fixes several security issues. zlib 1.4's CMake renamed and added options, so the fetch now turns off `ZLIB_BUILD_TESTING` (its tests would join carquet's `ctest`), `ZLIB_BUILD_SHARED` and `ZLIB_INSTALL` (it no longer reads `SKIP_INSTALL_ALL`), and the export of the bundled archives drops zlib's new `PUBLIC_HEADER` list, so the install prefix still gets no `zlib.h` that could shadow the system one. xmake-repo does not list 1.4 yet: `zlib v1.4` resolves through the package's git URL to the upstream tag. Builds against a system zlib are unaffected. Checked: full test suite with the bundled 1.4 under ASan / UBSan, `cmake --install` plus a `find_package(carquet)` consumer writing a GZIP file that pyarrow reads, and the xmake CLI reading pyarrow GZIP files.
- **lz4 package config found under both spellings** ([#29](https://github.com/Vitruves/carquet/issues/29), suggested by @burunda-ham): `find_package(lz4 CONFIG NAMES lz4 LZ4)` also finds an `LZ4Config.cmake`, which `find_package(lz4)` misses on case-sensitive file systems.

### Performance

Real-world files (OPTIONAL columns with nulls, dictionary encoding, strings: what pyarrow and Arrow write by default) and the C default `use_mmap = false` took slow paths on both sides: the batch reader's parallel pipeline only ran for fixed-width REQUIRED columns of a memory-mapped compressed file, and the writer's page-parallel / pipelined encode only for REQUIRED PLAIN / BYTE_STREAM_SPLIT columns. Both now cover these cases. Output bytes of REQUIRED columns and the paths the existing benchmark configs measure are unchanged (within noise).

Against Arrow C++ 26.0.1 on the same machine, carquet now wins every config of the reference benchmark, nullable included (reads 1.4–2.1x, writes 1.4–7x); before, nullable reads were 2–3x slower than Arrow's.

Reader (`batch_reader.c`, `arrow_c_export.c`, `core/file_io.c`):
- **Definition levels as bits**: for flat nullable columns (`max_def == 1`, `max_rep == 0`, the common case) the 1-bit level stream is decoded straight into a validity bitmap (`carquet_rle_decode_to_bitmap()`): each RLE run or bit-packed group is a 64-bit OR, non-null counts are popcounts, and values are spread from the bits 8 rows at a time. One int16 per row was decoded before, counted three times and re-packed into the bitmap, which cost more than LZ4 decompression on nullable files. int16 levels are still produced, from the bits, for callers that ask for them (`carquet_column_read_batch()` with `def_levels`). Fixed-width PLAIN pages of these columns are read in place from the page payload instead of being copied first. The int16 decoder (nested and `max_def > 1` columns) expands 1-bit groups directly and fills short RLE runs inline. CPU per read −10 to −46 % on top of the pipeline work below.
- **Flat OPTIONAL columns in the pipeline**, BYTE_ARRAY included (`max_rep == 0`): values are read from the decoded pages straight into their rows (16K-row blocks, branch-free spread; previously one variable-size `memmove` per row after a dense copy) with the validity bitmap, the same row-aligned layout as before. Segments of one chunk write the bitmap bytes they own and hand the shared edge bytes to the consumer, which merges them; a batch that does not start on a byte boundary gets a shifted copy of the bitmap, otherwise a view. String values stay valid because a slot's column readers are only rebound when that slot is refilled. Installing a page filter on such a reader switches it to the sequential filtered path.
- **Segments for chunks the coalesced path cannot decode** (dictionary or other encodings, levels): each segment decodes through its own column reader, positioned with `carquet_column_reader_seek_to_data_page()`. Every segment decodes the dictionary page again, so a dictionary chunk is cut into at most `1 + data / (8 × dictionary)` segments. The split planner measures a chunk from its dictionary page, which `total_compressed_size` includes.
- **Uncompressed files** go through the pipeline when a column has definition levels or a dictionary (zero-copy could not serve those columns anyway).
- **Positional reads without mmap**: a reader that opened its file itself reads pages with `pread()` (`ReadFile` with an offset on Windows) instead of `fseek` + `fread` on the shared `FILE*` (`carquet_file_pread()`). Column readers can then load pages from several threads, which enables the pipeline and the column-parallel batch loop without mmap. Readers over a caller-supplied `FILE*` keep `fseek` + `fread`.
- **Memory**: pipeline depth is capped so all slots fit 256 MB (at least 2 slots); wide or string-heavy row groups get fewer slots. Slot buffers are reference-counted (see below).
- **Builds without OpenMP** (the macOS / Windows Python wheels) size the pipeline pool from the CPU count instead of 4 threads.
- **Arrow export** (the Python package's path): fixed-width columns are exported zero-copy when the batch covers at least a quarter of its row group; the ArrowArray holds a reference on the pipeline's buffer, which stays valid after the batch and the reader are freed (the last release frees it, from any thread). Null counts use popcount instead of a per-bit loop; strings are copied with inline moves, in parallel 64K-row ranges. Python `read_table`, same files: REQUIRED 12.4 → 8.4 ms, OPTIONAL 18.8 → 12.3 ms, 7 % nulls 30.7 → 14.9 ms, pyarrow defaults 19.6 → 14.0 ms, strings 377 → 96 ms.

Writer (`column_writer.c`, `row_group_writer.c`, `file_writer.c`, `page_writer.c`, `encoding/dictionary.c`, `encoding/rle.c`), 10M rows, 3 columns, min of interleaved runs, LZ4 / Snappy (REQUIRED: 65–70 ms, unchanged):

| columns | v0.7.3 | this release |
|---|---|---|
| OPTIONAL, 10 % nulls | 188 / 191 ms | 81 / 77 ms |
| REQUIRED + one dictionary column | 148 / 138 ms | 58 / 57 ms |
| OPTIONAL, 10 % nulls + one dictionary column | 207 / 198 ms | 72 / 65 ms |

- **The pipelined encode accepts every row group**: columns that cannot be cut into page tasks run on the pipeline pool as one task each, through the same code as the serial path, so row groups overlap each other and the I/O whatever their column types (bloom-filter and page-index writers keep the fork/join path).
- **OPTIONAL fixed-width PLAIN / BYTE_STREAM_SPLIT columns are encoded page-parallel** (non-repeated, max definition level up to 7). The page flush rule now charges definition levels at their bit-packed size instead of their RLE size, so page boundaries follow from counts alone; each page task replays the serial encoder's chunks, so the bytes match the serial path.
- **Dictionary columns**: for 4- and 8-byte values the dictionary is built with word compares, a pre-mixed multiplicative hash at a low load factor (collisions, not hashing, were the cost: ~15 ns per extra probe) and reuse of the previous index for repeated values; same entry numbering and size cap. Min / max are computed over the dictionary entries instead of every value.
- **Batch RLE encoders**, byte-identical to the per-value encoder: maximal runs of 8 or more become RLE runs and the stretches between them are bit-packed in one go, written straight into the buffer. 1-bit definition levels go through a new dispatched `levels_to_bits` kernel (NEON / SSE / scalar) and their groups are copied out of the bit array; dictionary indices check only aligned 4-value blocks for runs and pack groups of width <= 8 with one 64-bit store. Levels: 2.66 → 0.73 ns per value at 10 % nulls; indices of width 7: 3.56 → 0.29 ns. Definition levels are walked once per call (`carquet_rle_encode_levels_counted()` returns the null count used for statistics and the level histogram), page tasks no longer recount nulls, and the page planner's plan is cached between its counting and filling calls. Differential tests at bit widths 0–32 against the per-value encoder and the dictionary build against a naive reference.
- **Dictionary data pages are cut by size** like Arrow (encoded indices plus levels against `page_size`) and respect `max_rows_per_page`; a dictionary chunk was always written as one data page, which also kept readers from splitting it. Each page carries its own statistics (NaN skipped, ±0.0 normalised).

Output bytes that change: dictionary chunks larger than one page (now several pages); OPTIONAL fixed-width columns when the RLE size and the bit-packed estimate of the levels fall on opposite sides of `page_size` (typical data, e.g. 10 % random nulls, gives the same pages); files that hit the row-group bug below. pyarrow 26 reads every combination back value for value (7 codecs, V1 / V2 pages, 16 KB to 1 MB pages, async I/O on / off, statistics and encodings checked), and `interop/run_interop.py` passes (pyarrow and DuckDB, both directions).

Bug fixes found on the way:

### Security / Bug Fixes

Memory safety (crafted input; every fix below except the hardening items has a test in `tests/test_security_hardening.c` that fails on the previous sources):
- **High**: a repeated geospatial_types field in a column's metadata wrote past `types[64]` and over `num_types`, letting the file choose the write position (`parquet_types.c`); the bound now uses the running count.
- **High**: multi-threaded mmap reads summed page `num_values` without a bound, so a split segment could write megabytes past its buffer (`batch_reader.c` `plan_coalesced_column_splits`); splits are rejected unless the page counts sum to the row count, and the chunk range check is overflow-safe.
- **High**: after a pipelined flush failed, the in-flight row group stayed referenced as current, so close/abort freed it twice and later writes raced with the encode tasks (`file_writer.c` `flush_row_group`); the reference is dropped on failure, the I/O error is sticky, and `carquet_writer_write_batch()` returns it.
- DELTA_BYTE_ARRAY prefix lengths were not validated (a 24-byte page could request 16 GiB; on 32-bit the size wrapped into a heap overflow); prefixes are checked, sums are checked and the total is capped at `INT32_MAX`. DELTA_LENGTH_BYTE_ARRAY bounds each length incrementally (the 32-bit sum wrapped past the bounds check).
- Schema validation at open: `num_children` must cover the element list (unreached leaves aliased the root), FLBA needs `type_length > 0`, FLOAT16 must be FLBA(2); the page filter takes the float16 path only for 2-byte FLBA (1-byte over-read).
- Arrow import rejects leaf types or levels that do not match the writer column (an int32 leaf into an INT64 column over-read the heap), struct child-count mismatches, NULL `children`, non-empty values without a data buffer, lengths above `INT32_MAX` and offset overflow.
- `ARROW:schema` decoding matches field names in place, caps the field loop and budgets the copied bytes (memory amplification).
- `carquet stat` read raw statistics as full INT64 / DOUBLE / INT96 / FLBA values without checking their length (unaligned over-read); it prints `(invalid)` for short values.
- Hardening: OffsetIndex rows are clamped into the row group and a negative `first_row_index` is rejected; 32-bit size wraps fixed in the PLAIN, BYTE_STREAM_SPLIT and dictionary size checks and in `carquet_column_retain_page()`; a failed `pthread_key_create` for the ZSTD context falls back to the context-free API instead of using an invalid key; unaligned `*(const int32_t*)` loads in SSE/AVX2 bit-unpack replaced by `memcpy`; the nested-list allocation cap counts the level arrays; an int32 truncation in a zero-copy check.

Reader (found by the corrected interop check and the fuzzers; tests in `tests/test_fuzz_regressions.c`):
- The batch reader looped forever on a nested file whose row group declares 0 rows while its columns hold values (`carquet_validate_file()` never returned); each row group is emitted once and empty ones are skipped.
- A dictionary page with `dictionary_page_offset` missing (old parquet-mr) failed with "Expected data page", and an offset of 0 was mishandled; `page_reader.c` detects the dictionary page itself.
- GZIP pages made of several concatenated gzip members decoded only the first.
- Plain LZ4 data under the Hadoop-LZ4 codec id was rejected; it now falls back to raw LZ4.
- A footer field written with the wrong type (Dremio's field 15) desynchronised the whole footer parse; such fields are skipped.
- `carquet_validate_file()` accepted files without the leading `PAR1` magic.
- `carquet_schema_column_name()` returns `""` instead of NULL for an unnamed column.
- Row-group pruning for `IS_NULL` / `IS_NOT_NULL` page-filter clauses read an uninitialised `has_null_count` (`page_filter.c` `rg_stats_might_match`, found by the Python suite under UBSan).

Writer:
- The `ARROW:schema` footer entry stored DECIMAL columns with precision 0 (the precision was taken from the legacy `SchemaElement` field, unset for schemas built from logical types), so Arrow C++ / PyArrow rejected the whole file ("Decimal precision out of range"); the Python package writes this entry by default, so every decimal file it wrote was affected. Precision and scale now come from the logical type, and precisions above 38 are tagged decimal256 (`arrow_schema.c`, test in `test_writer_extensions`).
- `carquet_writer_set_column_bloom_filter()` had no effect on its own: enabling a column with the global option off wrote no filter, disabling one with it on was ignored (test in `test_writer_extensions`).

Threading:
- `carquet_worker_pool_create()` could hang forever when thread creation failed after some workers had started (address-space or commit exhaustion, `ulimit -u` / cgroup `pids.max`, …): the failure path set `shutdown` and broadcast without the pool lock, so a worker between its check and its wait missed the wake-up and the creator blocked joining it ([#37](https://github.com/Vitruves/carquet/issues/37)). Writer close (pipelined encode pool) and the non-OpenMP batch-reader column pool were affected. The failure path now tears down the started threads through `carquet_worker_pool_destroy()`, which signals under the lock (`worker_pool.c`).

CLI:
- `head`, `tail`, `sample` and `cat` used the node's own definition level instead of the column's accumulated maximum (crash in `sample` on nested files); negative row counts, invalid types and failed reads led to bad allocations or writes before the buffer. Same level mistake fixed in the generated reader code (`codegen_read.c`). 4,800+ sanitizer CLI runs over the corpus and fuzz inputs are clean.

Windows (first run on Windows hardware; MSVC 19.44, clang-cl, MinGW-w64 GCC 16; tests in `tests/test_platform_io.c` unless noted):
- **High**: MSVC x86 at `/O1` / `/O2` miscompiles the 64-bit `while (value > 0) { width++; value >>= 1; }` loop of `bit_width_required()` (`delta.c`): it returns 32 less than the right width for values ≥ 2³² (reproduced standalone; x64, `/Od` and GCC/Clang are fine). 32-bit Windows builds therefore wrote DELTA_BINARY_PACKED INT64 pages whose deltas need more than 32 bits with too few bits, without any error. It now uses `carquet_bit_width64()`; the other bit-width loops in `src/` are not affected. Caught by the existing `test_encoding_roundtrip` on Win32.
- Non-ASCII paths: `fopen`, `remove` and `CreateFileA` read paths in the ANSI code page, so a UTF-8 path with any non-ASCII character could not be read, mmapped, appended to or removed on abort, and the writer created a file under a garbled name. Bindings send UTF-8 (Python's `os.fsencode()` on Windows, PEP 529), so this broke non-ASCII paths in the Windows wheel. New `src/core/file_io.{c,h}`: valid UTF-8 paths go through `_wfopen` / `_wremove` / `CreateFileW`; ASCII and legacy ANSI (non-UTF-8) paths keep the narrow calls. POSIX unchanged. The CLI rebuilds `argv` as UTF-8 from `GetCommandLineW()` and switches the console output code page to UTF-8 while it runs (restored at exit).
- mmap reader: the file is opened with `FILE_SHARE_DELETE` (it can be renamed or deleted while mapped, as on POSIX); empty files and, on 32-bit builds, files larger than `SIZE_MAX` are refused before `CreateFileMapping` / `mmap` instead of truncating the size, and the reader falls back to the `fread` path, which reports the proper error.
- 32-bit builds: `read_footer` cast the file size to a 32-bit `size_t`, and the page-offset bounds checks (`page_reader.c`, `reader_read_bytes`, the prebuffer lookup) compared truncated 64-bit offsets; files over 4 GB now get a clear error and offsets are compared in 64 bits. The buffer writer no longer returns a silently shortened buffer with success past 4 GB. The `carquet_dictionary_decode_*` helpers check their allocation size for wrap.
- Arrow import: the fixed-size-list count was parsed with `strtol` (32-bit on Windows), so `+w:4294967298` was clamped and accepted; now `strtoll` (test in `test_arrow_c_data`).
- `carquet_writer_get_buffer()` said to release the buffer with `free()`, which corrupts the heap when carquet is a DLL on another C runtime (Debug vs Release, `/MT`, MinGW vs MSVC) or a custom allocator is set; release it with the new `carquet_free()`. The docs now also say that a successful call releases the writer (`carquet_writer_abort()` afterwards is a use after free).
- SIMD dispatch: the AVX2 path also requires FMA, BMI1 and BMI2, and the AVX-512 path CD and DQ, since `/arch:AVX2` / `/arch:AVX512` let MSVC emit them anywhere in those files; a CPU or hypervisor exposing AVX2 without them would have faulted. `carquet_popcount32/64` used the POPCNT instruction unconditionally under MSVC (not baseline x86-64); it now does so only in `/arch:AVX` and higher builds (both helpers are currently unused).
- An unchecked `carquet_offset_index_get_page_location()` status in the batch reader left `loc` uninitialised on failure; it now returns an error. `ensure_column_overrides()` rejects a negative column count before sizing its arrays (GCC LTO `-Wstringop-overflow`).

### API / Docs

- New `carquet_column_reader_reset()`: moves a column reader to another row group of the same column and keeps its page / decode / scratch buffers, so a row-group-by-row-group column-reader scan allocates its decode buffers once instead of once per row group × column ([#38](https://github.com/Vitruves/carquet/issues/38)). The batch reader already reused its column readers this way; both now share the same reset code. Test in `test_advanced_api`.
- New `carquet_free()`: releases memory that carquet hands to the caller (`carquet_writer_get_buffer()` output) through carquet's allocator and C runtime. Use it instead of `free()`.
- New `carquet_reader_read_arrow_fields()`: `carquet_reader_read_arrow()` restricted to some top-level fields (in the order given); only the leaf columns under them are read and decoded. Tests in `test_arrow_nested`.
- `carquet_arrow_export_batch()` accepts batches from a projected (or reordered) batch reader when given the reader's schema: the fields whose leaves are all projected are exported in projection order, a partly projected field (a MAP key without its value) is rejected. Before, any projection was refused, and a full projection in another order was exported under the wrong names. Tests in `test_arrow_c_data`.
- `carquet_filter_clause_t`: the header said FIXED_LEN_BYTE_ARRAY `IN` values are `carquet_byte_array_t` entries; the page filter reads them as raw values packed at `type_length` stride (the implementation's documented layout), so the header now says that.
- `carquet_schema_node_max_def_level()` / `carquet_schema_node_max_rep_level()` were documented as the column's maximum level; they return the node's own contribution (0 or 1). The docs now say so and point to `carquet_schema_max_def_level()` / `carquet_schema_max_rep_level()`.

### Performance

All numbers below are from the reference benchmark (`benchmark_carquet`, 3 REQUIRED columns, Release + LTO + `-march=native`) on a quiet Apple M3, as the median of 5 interleaved rounds; "each change alone" compares the full tree with a copy where only that change is reverted. Medium is 1M rows in 10 row groups of 100k, large is 10M rows in 10 row groups of 1M.
- Snappy compressor: after a short match the next hash lookup reuses words already loaded for the comparison, and literals of up to 60 bytes followed by a copy move in 16-byte chunks; byte-identical output. Alone: Snappy write −7 % large (52.0 → 48.3 ms), −8 % medium (6.86 → 6.29 ms); the end-to-end gain is smaller than the compressor's own because compression overlaps with the rest of the pipeline.
- Snappy decompressor: the two copy-offset checks merged into one unsigned compare, the output-length check moved off the fast paths (300k-case differential mutation fuzz identical to the previous decoder). Alone: Snappy read −6 % large (12.6 → 11.9 ms), −3 % medium (1.32 → 1.28 ms).
- Pipelined write: up to 8 row groups in flight instead of 2, while everything in flight fits a 64 MB raw budget (a 20 MB row group allows 3 in flight; row groups above 32 MB keep the one-behind pipeline); finished row groups are completed at the next flush so their I/O starts promptly. Peak memory can grow by up to 64 MB of raw input. Alone: write medium snappy −10 %, zstd −16 %, lz4 −12 %, none ±0; large none −17 % (60.5 → 50.5 ms), compressed large within noise (±3 %).
- Batch reader: pipeline workers read from the reader's existing file mapping instead of one `mmap` / `munmap` per row group, and the main thread prefaults each row group with `madvise(MADV_WILLNEED)`. Alone: read medium snappy −15 % (1.51 → 1.28 ms), lz4 −20 % (1.11 → 0.89 ms), zstd −2 %; large lz4 −6 %, snappy −3 %, zstd within noise.
- Whole tree vs v0.7.2, same interleaved runs: medium write snappy −19 % (7.77 → 6.29 ms), zstd −16 % (9.31 → 7.83 ms), lz4 −11 % (7.91 → 7.01 ms), none ±0; medium read snappy −17 % (1.54 → 1.28 ms), lz4 −23 % (1.16 → 0.89 ms), zstd −3 %; large write none −14 % (58.5 → 50.5 ms), compressed large writes and reads within ±5 % except snappy read −6 %. `run_benchmark.py --skip-xlarge` against the v0.7.2 reference JSON (large, W / R ms): none 74.7 / 0.36 → 60.5 / 0.27, snappy 52.7 / 12.4 → 45.4 / 11.5, zstd 60.4 / 19.8 → 59.0 / 19.9, lz4 57.2 / 9.2 → 50.9 / 8.3. Output bytes of every benchmark file are identical to v0.7.2 (`cmp`).
- Column-reader scans ([#38](https://github.com/Vitruves/carquet/issues/38)): `carquet_reader_prebuffer()` keeps its buffer across calls and reuses it while the next range fits (it was freed and re-allocated per row group); decode buffers are `malloc`ed instead of `calloc`ed (the decoder writes every value it reports); dictionary-index gathers for INT32 / INT64 / FLOAT / DOUBLE skip the separate bounds pass when `2^bit_width <= dictionary size` (the RLE decoder masks indices to `bit_width` bits, so none can be out of range). The remaining checked gathers on x86 now run the SSE / AVX2 / AVX-512 kernels that compare each block of indices against the dictionary size inside the gather loop, as ARM already did, instead of a separate scalar validation pass before the gather (the reporter's profile had that pass at 8.5 % of cycles next to 11.5 % for the gather); differential test in `test_core`. Not yet timed on x86 hardware. With an allocator that `mmap`s blocks of 128 KiB and more (glibc's default threshold), a 30-row-group, 2-column scan read 3 times went from 180 `mmap` calls and 11,700 minor faults to 2 and 145 with `carquet_column_reader_reset()`; the reporter measured page faults at about half of a ClickBench `hits.parquet` scan on glibc.
- Builds without OpenMP (the macOS and Windows Python wheels) decoded a batch's columns one after another; the prefetch and read loops of the batch reader now run one column per thread on a persistent worker pool under the same conditions as the OpenMP path, and `carquet_arrow_export_batch()` exports large batches field-parallel (OpenMP, or that pool). PyArrow-written 5M-row file with 5 nullable columns, Apple M3, no OpenMP: zstd 167 → 78 ms, snappy 106 → 56 ms, uncompressed 95 → 53 ms (full read through the Python package).
- x86 bit-unpacking (every OS; measured on Windows): the AVX2 kernels were never used above 8 bits. One shuffle + `vpsrlvd` kernel now covers widths 5–25, plus copy kernels for 16 and 32 (the byte-at-a-time 5–7 kernels are gone); it reads only the bytes the caller guarantees (checked exhaustively against a reference model). The scalar fallback above 8 bits does one 8-byte load per value instead of byte by byte. ### Performance

- Compressed reads: page-range segment tasks per column chunk (no column reader shared between tasks; a short segment triggers a consumer-side re-read with full error detail), `MAP_SHARED` mappings + `madvise(MADV_WILLNEED)` on the fill thread, direct NEON BYTE_STREAM_SPLIT transpose on ARM64 for pages up to 1M values. Reference benchmark read: snappy 14.9 → 12.4 ms, lz4 10.2 → 8.4 ms, zstd 21.5 → 19.3 ms; a single-row-group 10M-row Snappy file 28–30 → 10 ms.
- Compressed writes: row groups encoded in a pipeline on a persistent worker pool (two alternating row-group writers; mixed/serial columns keep the OpenMP path), pages written straight from the encode buffers (no row-group copy), heaviest pages scheduled first. Reference benchmark write: snappy 53.6 → 48.4 ms, zstd 64.4 → 55.0 ms, lz4 57.2 → 49.3 ms; `none` stays at the kernel `write()` floor. Peak memory grows by about one row group of raw input.
- Nullable columns read in small batches: the dense-value offset is carried by a cursor instead of recounting the consumed levels on every call. 2M-row OPTIONAL INT32 read 256 values at a time: 497 ms → 1.8 ms.
- RLE encoder: bit-packed groups share one header per 63 groups (parquet-mr behaviour); every level stream and `RLE_DICTIONARY` index stream shrinks (uncompressed file with a 50 %-null INT32 column and a 200-value dictionary string column: −7 %).
- Batch-reader pipeline waits for its head slot only instead of draining the whole pool at every row-group transition (structural; unchanged wall time on the reference file).
- DELTA_BYTE_ARRAY: length streams decoded once instead of twice; encoder no longer rescans each common prefix.
- GZIP: zlib streams cached per thread (`inflateReset` / `deflateReset`), freed by `carquet_cleanup()`.
- AVX2 `pack_bools`: 32 booleans per iteration with `cmpeq` + `movemask` instead of an 8-wide multiply / horizontal-add sequence (2.3× faster in a differential harness under Rosetta; byte-exact with scalar).

## v0.7.1

Additive read-side release closing two P3 Arrow-parity gaps (a predicate-independent row-range read and the module-level dictionary decode API for the byte types), plus a batch of memory-safety and correctness fixes and internal performance improvements to the encode / decode hot paths (no output-byte change). No breaking API change (new functions are appended, and one field, `async_io`, is appended to `carquet_writer_options_t`, which grows the struct: rebuild against the new header). **Default output bytes are unchanged except for two corrected-behaviour cases**: byte-backed `DECIMAL` columns containing negative values now record spec-correct signed min/max statistics (previously an unsigned-lexicographic comparison inverted them), and dictionary-encoded (categorical) Arrow arrays written via `carquet_writer_write_arrow()` now emit their resolved values instead of the raw index buffer.

### API

- **Failure detail for the batch reader — `carquet_batch_reader_last_error()`**: `carquet_batch_reader_next()` has no error out-parameter, so every message built deeper in the reader was discarded and a failing scan surfaced only a status code — on a decode failure the coarse `CARQUET_ERROR_DECODE`, with no indication of which column, page, or file offset was involved. The batch reader now retains the failure and hands it back as a `const carquet_error_t*` (NULL when the last `next()` did not fail; `CARQUET_ERROR_END_OF_DATA` is the normal terminator and leaves it unset). When the failure came from a column read the error is that column's verbatim error, so its `code` is the *underlying, more specific* status — a corrupt Snappy page returns `CARQUET_ERROR_DECODE` from `next()` while `last_error->code` is `CARQUET_ERROR_INVALID_COMPRESSED_DATA` and the message names the page's absolute file offset and the exact codec check that fired. Failures outside a column read fall back to the status name, so the code always matches `next()`'s return. Internally, each failure site in the batch reader's column and nested-list read paths now records a specific message on its own column reader (a per-thread write — the parallel column loop gives each thread its own reader), and the reads go through `carquet_column_read_batch_ex()` so page/codec detail propagates verbatim. Additive: no existing signature or struct layout changes.
- **Arbitrary `[offset, limit)` row-range read — `carquet_batch_reader_set_row_range()`**: restricts a batch reader to an arbitrary logical row window independent of any predicate (previously only value-level `carquet_column_skip` existed). `next()` then yields exactly the requested rows, in order, across as many batches as needed. Row groups entirely outside the window are skipped with no I/O; the leading rows of a partially-selected row group are skipped via the offset index when present, otherwise by read-and-discard. `offset == 0 && limit < 0` clears the range (full read); a negative `limit` means "to end of file"; an out-of-range `offset` yields no rows. The feature is mutually exclusive with an installed page filter (either activation while the other is active returns `CARQUET_ERROR_INVALID_ARGUMENT`) and is not combined with repeated (nested) columns (`CARQUET_ERROR_NOT_IMPLEMENTED`). Drives a dedicated sequential path, bypassing the parallel pipeline.
- **Background row-group writes — `carquet_writer_options_t.async_io`** (default `true`): once a row group is encoded, its column chunks are handed to a dedicated I/O thread and written while the caller's next batches are buffered, encoded and compressed, so the kernel copy into the page cache (about 4 GB/s on Apple Silicon, roughly 45 ms per 200 MB, and previously fully serialized with everything else) overlaps with encoding instead of stalling it. At most one row group is in flight and its buffers are recycled, so peak memory grows by about one encoded (compressed) row group. A failed background write is sticky and surfaces from the next row-group flush or from `carquet_writer_close()`; `carquet_writer_abort()` drains before closing. Bloom filters, page indexes and the footer are written only after the queue is drained, so file layout is unchanged — output is byte-identical with the option on or off (asserted by `tests/test_parallel_write.c`). Set `async_io = false` to keep every write on the calling thread (options structs zero-initialized by hand, rather than through `carquet_writer_options_init()`, also get the synchronous behaviour).
- **Complete module-level dictionary decode for the byte types — `carquet_dictionary_decode_byte_array()` / `carquet_dictionary_decode_fixed_len_byte_array()`**: the `src/encoding/dictionary.c` decode API was asymmetric — INT32/INT64/FLOAT/DOUBLE had module decoders but BYTE_ARRAY and FIXED_LEN_BYTE_ARRAY were only decoded inline in the reader. Both are now exposed (declared in the new `src/encoding/dictionary.h`), mirroring the encode side: BYTE_ARRAY yields `carquet_byte_array_t` values aliasing into the caller's dictionary buffer (length-prefixed PLAIN layout, every length validated against `dict_size`); FLBA yields a contiguous fixed-width buffer. Every index is validated against `dict_count`. No behaviour change to the reader, which continues to use its inline fast path.

### Security / Bug Fixes

- **Fix `DELTA_BINARY_PACKED` mini-blocks wider than 32 bits being written and read byte-aligned instead of bit-packed** (`src/encoding/delta.c`): a mini-block whose deltas need 33 to 64 bits was stored as one whole little-endian value of `ceil(width / 8)` bytes per delta, in both the encoder and the decoder. The spec bit-packs every width, so 32 deltas of 33 bits are 132 bytes, not 160. The two sides agreed with each other, so carquet round-trips passed, but the layout only coincides with the spec at widths 40, 48, 56 and 64: an `INT64` column with large jumps (hashes, random ids, nanosecond timestamps across gaps) written by pyarrow / parquet-mr / DuckDB decoded to wrong values with no error, and the same column written by carquet was unreadable elsewhere. Wide mini-blocks now go through a 64-bit LSB-first pack/unpack. `INT32` deltas are also computed modulo 2^32, as the other writers do, so an `INT32` column spanning more than half the type's range no longer produces a 33-bit mini-block that pyarrow rejects. **Output bytes change** for `DELTA_BINARY_PACKED` columns with such deltas; files written with them by an earlier version must be regenerated. Verified in both directions against pyarrow 23 for every width from 33 to 64. Regression tests: `delta_binary_packed_i64_wide` and `delta_wide_layout` (hand-derived bytes) in `tests/test_encoding_roundtrip.c`.
- **Fix silent corruption of every `DELTA_*` page assembled from more than one encode call**: the same defect as the `BYTE_STREAM_SPLIT` one below, for `DELTA_BINARY_PACKED`, `DELTA_LENGTH_BYTE_ARRAY` and `DELTA_BYTE_ARRAY` (including `DELTA_BYTE_ARRAY` on `FIXED_LEN_BYTE_ARRAY`). Each `carquet_page_writer_add_values()` call emitted a complete delta stream, header included, so a page fed by several `carquet_writer_write_batch()` calls (or by one batch the column writer cut into chunks that shared a page) held several concatenated streams while a reader decodes one, sized by the first header. Values after the first call came back wrong or the page failed to decode. Raw values now accumulate in the page and are encoded once at finalize (`apply_delta_encoding()`, `src/writer/page_writer.c`), which also covers the header-only stream an all-null page needs. Page boundaries for these encodings are now cut on the unencoded size, so pages are somewhat smaller after encoding than before. Files written through the affected pattern must be regenerated. Regression tests: `delta_*_chunked` in `tests/test_encoding_roundtrip.c`.
- **Fix the mmap batch reader returning zero rows, with `CARQUET_ERROR_END_OF_DATA`, for highly compressible multi-row-group files**: the pre-read pipeline rejected any row group holding more rows than `file_size * 8` as malformed, on the reasoning that a row needs at least one bit, and reported the rejection as a normal end of data. A constant or low-cardinality column under any codec (or RLE runs) packs far more rows per byte than that: a 4-row-group, 4-million-row constant `INT64` file is 3.7 KB. Such files now take the sequential path, whose buffers are bounded by `batch_size`, so the allocation guard still holds without refusing valid data. Regression test: `mmap_highly_compressible` in `tests/test_mmap.c`.
- **The mmap pre-read pipeline no longer turns a failure into a normal end of data, or exposes a column that was not fully read** (`src/reader/batch_reader.c`): worker tasks recorded how many values each column produced, but nothing read those counts back, so a column that failed or came up short was served at the row group's full size over a buffer that was uninitialized or still held the previous row group. Allocation, column-open and page-filter failures while filling a slot simply returned, which the caller saw as `END_OF_DATA` (a page-filter evaluation error skipped the row group, dropping its rows). Every column's count is now checked against the slot's row count before any of it is exposed, fill failures are recorded, and either one is returned from `carquet_batch_reader_next()` with detail in `carquet_batch_reader_last_error()` and stays returned on later calls. The sequential path also treats a positive count returned together with an error as a failure. Regression test: `mmap_pipeline_corruption` in `tests/test_mmap.c`.
- **The coalesced column fast path now does the same checks as the page-by-page reader**: it skipped page CRC verification even with `verify_checksums` set, did not check that a PLAIN page decompressed to the size its header declared, and sent every `BYTE_STREAM_SPLIT` width other than 4 through the 8-plane `double` transposer, which is wrong for `FIXED_LEN_BYTE_ARRAY` (and `INT96`). CRCs are verified, short payloads fall back to the standard reader, and other widths use the generic transposer. Part of the fast path's earlier speed advantage came from skipping the CRC, so read benchmarks on files with page checksums are not directly comparable with previous versions.
- **Fix chunk-level min/max statistics that excluded a page whose minimum is the empty string**: the column writer skipped any page whose min or max had zero length when folding page statistics into the chunk's, treating it as "no statistics". For a `BYTE_ARRAY` column the empty string is a real minimum, so a page holding `""` and `"zzz"` was left out and the row group could publish a maximum below `"zzz"`, letting readers prune row groups that contain matching rows. Such pages are now folded in. A chunk whose minimum is the empty string still publishes no min/max (the footer path does not yet distinguish an empty value from an absent one), which costs pruning but is correct. Regression test: `empty_string_chunk_stats` in `tests/test_page_filter.c`.
- **Fix `null_pages` in the column index marking every page without min/max as all-null**: the flag was derived from the absence of page statistics rather than from the value counts, so with `write_statistics = false`, for an all-NaN page, or for a type with no defined order, a page full of values was recorded as null and skipped by every value predicate. It is now set only when the page's null count equals its value count. Regression test: `no_stats_page_not_null` in `tests/test_page_filter.c`.
- **Fix Arrow `int8` / `uint8` / `int16` / `uint16` columns being read and produced with the 4-byte `INT32` stride**: these types map to `INT32` with an `INTEGER(8|16)` annotation. `carquet_writer_write_arrow()` read the Arrow values buffer four bytes per element, so a narrow integer array was read past its end and written as garbage; `carquet_arrow_export_batch()` and `carquet_reader_read_arrow()` declared the narrow Arrow format in the schema but filled the values buffer with 4-byte integers, which a consumer then reads as four times as many wrong values. Import now widens (sign- or zero-extending) and both exports narrow to the declared width. Regression test: `narrow_ints` in `tests/test_arrow_c_data.c`.
- **Reject out-of-range column projection indices in `carquet_batch_reader_create()`**: `config.column_indices` was copied and used to index the schema's leaf table with no bounds check, so a negative or too-large index read out of bounds. It now fails with `CARQUET_ERROR_INVALID_ARGUMENT`. Regression test: `projection_index_bounds` in `tests/test_edge_boundaries.c`.
- **Reject negative lengths in `carquet_encode_plain_byte_array()`**: `carquet_byte_array_t.length` is a signed `int32_t`; a negative value contributed 3 bytes to the reservation and was then copied as ~4 GB. Lengths are validated before anything is reserved. Regression test: `negative_byte_array_length` in `tests/test_edge_boundaries.c`.
- **Reject truncated dictionary index streams**: `carquet_read_data_page_v1/v2` tested the RLE decoder's return for `< 0`, which it never returns, so a stream that ended early was accepted and the rest of the index buffer (stale or uninitialized) was looked up in the dictionary. A count other than the page's non-null count is now `CARQUET_ERROR_DECODE`.
- **Smaller fixes**: the page-index builders and the CLI filter parser published reallocated arrays only after every `realloc()` had succeeded, leaving pointers to freed blocks in the structure if a later one failed; `thrift_skip()` consumed nothing for a boolean inside a list / set / map, where (unlike a struct field) each boolean is a byte of its own; `carquet_bitpack_32()` wrote a full `bit_width`-byte group for a trailing partial group and `carquet_bit_writer_write_bits()` could shift bits out of its 64-bit accumulator (neither is reachable from the library today); the CLI never counted its filter literals, so `cli_filter_free()` leaked them; and `CARQUET_ERROR_INIT` left `offset` / `column_index` / `row_group_index` at 0 where `carquet_error_init()` sets -1.
- **Fix silent corruption of `BYTE_STREAM_SPLIT` pages assembled from more than one encode call** ([#24](https://github.com/Vitruves/carquet/issues/24), [#31](https://github.com/Vitruves/carquet/issues/31)): the page writer transposed each `carquet_page_writer_add_values()` call's values into byte planes on its own and appended the result, so a page built from several calls held several independent transpositions, while every reader de-splits a page as a single transposition sized by its total non-null count — the values came back as garbage (`inf`, `±1e300`, denormals) with no error and with definition levels intact. There were two ways to get such a page: several `carquet_writer_write_batch()` calls landing in the same page, and one large batch on a nullable column, which the column writer cuts into row-count chunks (`page_size / value width`) but flushes on estimated size, so a null-heavy chunk stays under the threshold and the next chunk joins its page. `BYTE_STREAM_SPLIT` is the default data encoding for `FLOAT`/`DOUBLE` whenever a codec is set, so compressed nullable float columns were affected without opting in; uncompressed output was not (PLAIN bytes concatenate legally). Raw values now accumulate in the page and are transposed once, when the page is finalized (`apply_byte_stream_split()`, `src/writer/page_writer.c`), for all five physical types the encoding supports. This is a writer-side fix: files already written by an affected version stay corrupt and must be regenerated. Regression tests: `bss_*_chunked` and `bss_*_null_shrunk_chunk` in `tests/test_encoding_roundtrip.c`.
- **Fix silent corruption of `BOOLEAN` pages assembled from more than one encode call, for both value encodings** ([#25](https://github.com/Vitruves/carquet/issues/25)): a data page's booleans are one stream however many calls build the page, but `carquet_page_writer_add_values()` restarted it on every call. With PLAIN (the default for `BOOLEAN`, so no opt-in is needed) each call began on a fresh byte, so once the running count stopped being a multiple of 8 every later value sat on the wrong bit and read back wrong, with no error. With RLE each call appended its own 4-byte-length-prefixed block, while a reader decodes only the block the first prefix describes — pyarrow rejects such a page with "Unexpected end of stream" and carquet's own reader came up short. As with `BYTE_STREAM_SPLIT` there were two ways to get such a page: several `carquet_writer_write_batch()` calls landing in one page, and a single large batch on a nullable column, which the column writer cuts into row-count chunks that share a page because bit-packed values rarely reach the page-size threshold. PLAIN now resumes at the page's bit position (new `carquet_encode_plain_boolean_append()` in `src/encoding/plain.c`, driven by a per-page value count in the page writer); RLE keeps a single prefix per page that every call extends and re-patches. This also fixes `carquet_writer_write_batch()` failing with `CARQUET_ERROR_OUT_OF_MEMORY` for a batch of a nullable `BOOLEAN` column in which every row is null. This is a writer-side fix: files already written by an affected version stay corrupt and must be regenerated. Regression tests: `boolean_{plain,rle}_exact_page_bytes` and `boolean_{plain,rle}_multi_call_page` in `tests/test_writer_extensions.c` (the former assert hand-derived page bytes), and `plain_boolean_append` in `tests/test_encodings.c`.
- **Fix a heap over-read and silent value corruption writing nullable columns through the deferred-encode path** (reported externally, [#33](https://github.com/Vitruves/carquet/pull/33)): in an OpenMP build, a row group with more than one column and no page index stashes the input of each compressed, non-dictionary, fixed-width column in `write_batch()` and encodes it at finalize, in parallel. `stash_deferred_batch()` (`src/writer/column_writer.c`) copied `num_values * stride` bytes from the caller's values array, but that array is packed — for an `OPTIONAL` column it holds only the non-null entries. Every batch containing nulls therefore read `nulls * stride` bytes past the end of the caller's array (a 20 000-byte read from a 316-byte block in the regression test; the reporter hit a segfault on a mostly-null column), and the stash kept a null-sized gap after each batch that `drain_deferred()`'s packed replay cursor then walked into, so every value after the first `write_batch()` call of a row group was wrong, with no error and with null positions intact. The stash now copies exactly the non-null values, and the replay hands the page writer a valid dummy pointer when a column's stash holds no values at all (every row null), which it would otherwise reject. Builds without OpenMP never defer and were not affected. This is a writer-side fix: files already written by an affected build stay corrupt and must be regenerated. Regression test: `deferred_nullable_batches` in `tests/test_writer_extensions.c`.
- **Fix a corrupt first-data-page offset on dictionary-encoded column chunks whose data pages do not start immediately after the dictionary page** (reported externally). Both dictionary-load paths (`load_dictionary_page_mmap` / `load_dictionary_page_fread` in `src/reader/page_reader.c`) *unconditionally* discarded the writer's `ColumnMetaData.data_page_offset` and recomputed the first data page as `dictionary_page_offset + dict_header + dict_payload`. That override exists to work around writers (DuckDB) that point `data_page_offset` at the dictionary page, but it is wrong for any conforming file where something sits between the dictionary page and the first data page — a legal `index_page_offset` page, or writer-inserted alignment padding. In such a chunk the reader started parsing page headers *inside* another page, so `compressed_page_size` / `uncompressed_page_size` were read out of payload bytes and the codec was handed a byte range that is not a compressed block at all. Snappy then reported `CARQUET_ERROR_INVALID_COMPRESSED_DATA` on a file that PyArrow reads without complaint, and dumping the offending range and feeding it to `python-snappy` reproduced the same rejection — because the range itself was wrong, not the file. The offset is now resolved by `carquet_resolve_data_start_offset()`: the writer's `data_page_offset` is honoured, and the computed dictionary end is used only when `data_page_offset` is *provably* wrong (at or before the end of the dictionary page), which still covers the DuckDB case.
- **Snappy rejections now report which of the 13 checks fired, and where.** Every failure path in `carquet_snappy_decompress()` returned the same bare `CARQUET_ERROR_INVALID_COMPRESSED_DATA`, so a failure part-way through a multi-gigabyte file was untriageable without a debugger. The decoder is now driven by `carquet_snappy_decompress_diag()` (`src/compression/snappy.h`), which fills a `carquet_snappy_diag_t` with a distinct `carquet_snappy_reason_t`, the source and destination byte positions at the point of rejection, the declared uncompressed length, the failing tag byte, and the relevant operand (literal length / copy offset). The reader folds that into its `carquet_error_t` message together with the codec, the *absolute file offset* of the page, and both page sizes — e.g. `Failed to decompress data page at file offset 2214592512: snappy[10]: copy offset points before start of output [src=25 dst=20 declared=9242833 tag=30 op=100] (codec=1, compressed=1599289, uncompressed=9242833)`. The detail is placed ahead of the sizes because `carquet_error_t` messages are capped at `CARQUET_ERROR_MESSAGE_MAX`. Reachable from both read APIs: `carquet_column_read_batch_ex()` propagates the message verbatim, and `carquet_batch_reader_next()` exposes it through the new `carquet_batch_reader_last_error()`. `carquet_snappy_decompress()` keeps its previous signature and behaviour. Decoder behaviour is unchanged: verified against reference Snappy on 1,582 differential cases (structured and random payloads from 0 B to 12 MB) across all three build variants — NEON, SSSE3, and the scalar path MSVC builds use.
- **Fix a truncated thrift LIST / MAP inside a growable parse window being reported as a hard decode error.** `thrift_read_list_begin()` / `thrift_read_map_begin()` raised `CARQUET_ERROR_THRIFT_DECODE` when the element count exceeded the bytes left in the buffer. Callers that parse out of a window they can enlarge — `read_and_parse_page_header_fread()` grows its read window only on `CARQUET_ERROR_THRIFT_TRUNCATED` — therefore gave up instead of re-reading with more bytes. Both now report `CARQUET_ERROR_THRIFT_TRUNCATED`, which is what the condition actually means.
- **Fix a silent short read and an out-of-bounds write in the mmap coalesced column fast path** (`coalesced_read_column_range`, `src/reader/batch_reader.c`). A decompression or BYTE_STREAM_SPLIT decode failure mid-chunk did `break`, returning however many values had been produced so far as if that were the whole answer — silent data loss with no error. Those paths now `goto fallback` and re-read the column through the standard page-by-page reader. Separately, the page was decompressed straight into the caller's buffer using the *header's* `uncompressed_page_size` as the capacity, which is a claim from the file rather than the space that exists; a header whose uncompressed size exceeds `num_values * value_size` therefore overflowed the destination. The two are now required to agree, and the fast path is skipped otherwise.
- **Raise the page-header parse window in the mmap scan fast paths from 512 bytes to 64 KiB.** Page headers carry per-page statistics with untruncated min/max, so a wide `BYTE_ARRAY` column (parquet-mr routinely writes these) exceeds 512 bytes and was silently demoted to the slow path. The thrift parser stops at the struct's STOP byte, so the larger window costs nothing on ordinary headers.
- **DECIMAL(FLBA/BYTE_ARRAY) min/max statistics are now ordered as signed big-endian two's complement** (the Parquet-mandated SIGNED sort order for byte-backed DECIMAL), not unsigned-lexicographic. Previously a negative value (leading `0xFF…`) sorted above every non-negative one, so the writer recorded an inverted min/max — spec-invalid statistics that also drove predicate pushdown to discard row groups / pages that actually contained matching rows. Fixed on every comparison site: the page-level and column-chunk-level stat merges (`src/writer/page_writer.c`, `src/writer/column_writer.c`) and both reader pruning paths (`src/reader/statistics.c` `carquet_reader_row_group_matches` and the batch reader's page filter `src/reader/page_filter.c`), via a shared `carquet_compare_decimal_be()` in the new `src/core/decimal_cmp.h`. **Default-bytes change** for byte-backed DECIMAL columns whose value range includes negatives; INT32/INT64-backed DECIMAL was already correct (native signed integer order).
- **Dictionary-encoded (categorical) Arrow arrays are now written as their resolved values, not the raw index buffer.** `carquet_writer_write_arrow()` / `carquet_arrow_import_schema()` previously ignored `ArrowSchema::dictionary` / `ArrowArray::dictionary`, so a pandas categorical or pyarrow `DictionaryArray` of strings was silently written as its integer index column (wrong data, no error). The schema import, leaf-accumulator setup, and record shredder now resolve each index through the dictionary and write the value column. Primitive dictionary value types are supported; a non-primitive (nested) dictionary value is rejected with `CARQUET_ERROR_NOT_IMPLEMENTED` rather than corrupted.
- **Fix an out-of-bounds read exporting a dictionary-preserved nested (LIST) column to Arrow.** With `preserve_dictionaries = true`, a repeated (`max_rep_level > 0`) BYTE_ARRAY column that carried a dictionary page was decoded as 4-byte indices, but the nested-list reconstruction path reinterpreted that buffer as 16-byte `carquet_byte_array_t` values — producing wild pointers that `carquet_arrow_export_batch()` then dereferenced (found by fuzzing). Dictionary preservation is now disabled for repeated columns (the preserved-dictionary APIs only support flat columns); the reader fuzzer was extended to drive `carquet_arrow_export_batch()` over every batch.
- **Fix undefined behaviour passing a NULL pointer to `memcpy`/`memcmp` for an empty BYTE_ARRAY statistic** (UBSan, reported externally): a zero-length `BYTE_ARRAY` value reached the page-writer stat helpers with `size == 0` and a possibly-NULL min/max buffer. The zero-length copies and compares are now short-circuited.
- **Fix two memory leaks in `carquet_delta_decode_int32/int64` on a malformed DELTA header** (reported externally): `delta_decoder_init()` heap-allocates its mini-block scratch before parsing the rest of the header, so a truncated header leaked it. The init error paths now free the scratch, covering every caller.
- **Fix a stack-overflow denial-of-service opening a malformed file** (`src/thrift/thrift_decode.c`): `thrift_skip()` recursed for every element of a LIST / SET / MAP container, but only the STRUCT path was depth-limited (the `THRIFT_MAX_NESTING` cap in `thrift_read_struct_begin`). A footer nesting containers to arbitrary depth (e.g. a long run of LIST-of-LIST headers) therefore recursed one C stack frame per level, bounded only by the footer size, and could exhaust the stack during `carquet_reader_open()`. Container recursion is now charged against `nesting_level` and rejected past the same cap.
- **Fix a 32-bit length-overflow guard in `carquet_rle_decode_levels_prefixed()`** (`src/encoding/rle.c`): the bounds check `4 + rle_length > input_size` was evaluated in 32-bit, so a prefix near `UINT32_MAX` (e.g. `0xFFFFFFFF` wrapping to `3`) passed the check and handed a ~4 GB length to the decoder over a tiny buffer — a large heap overread. Widened to 64-bit (`(uint64_t)rle_length + 4 > input_size`), matching the reader's other prefix checks. This exported helper has no in-tree caller today (the reader decodes V1 levels through its own already-widened path), so the fix closes a latent API/fuzzing landmine rather than a reader-reachable bug.
- **Fix unbounded recursion on empty RLE runs in `start_new_run()`** (`src/encoding/rle.c`): a zero-length run tail-recursed to fetch the next run, so a page of zero-length-run headers recursed one frame per header (elided only under optimization/TCO — a Debug/fuzz-build overflow). Converted to a loop.
- **CLI: render `TIME` columns as a time of day instead of a raw integer** ([#21](https://github.com/Vitruves/carquet/issues/21)): `cli_format_value()` special-cased `DATE` and `TIMESTAMP` but had no `TIME` branch, so a `TIME(MILLIS)` / `TIME(MICROS)` / `TIME(NANOS)` column (whether annotated via LogicalType or the legacy `TIME_MILLIS` / `TIME_MICROS` ConvertedType) printed its underlying INT32/INT64 in every command — `head`, `tail`, `cat`, `sample`, `stat` min/max, and `export --format csv`. TIME values now print as `HH:MM:SS.frac` with the fraction at the unit's full precision (`00:00:00.000` for millis, `.000000` for micros, `.000000000` for nanos), matching what PyArrow reports for the same file. Out-of-spec values (negative, or past 24 h) print readably with a sign and/or an hour field past 23 rather than wrapping. Also hardened the `TIMESTAMP` branch to require an INT64 physical type — a hand-crafted file annotating an INT32 column as `TIMESTAMP` previously drove an 8-byte load out of a 4-byte slot.
- **CLI (Windows): fix garbage `DATE` / `TIMESTAMP` output outside the C-runtime's supported time range.** Both branches converted through `gmtime_r` / `gmtime_s`, but the MSVC CRT rejects any time outside `[1970-01-01, 3000-12-31]` and returns `EINVAL` *without writing* `struct tm`; the return value was unchecked, so on Windows a pre-epoch or far-future value printed whatever was on the stack (e.g. `1899-00--1T-1:-1:-1`) — an uninitialized read, and wrong for a large part of Parquet's legal DATE range. Both branches now use a self-contained proleptic-Gregorian `civil_from_days()` (Howard Hinnant's algorithm), which is total over the whole `int64` domain and byte-identical across platforms; verified against `gmtime_r` day-by-day over the full DATE range (3,652,059 days, year 1 through year 9999, no mismatch). This also drops a latent 32-bit `time_t` overflow in the DATE path.

### Performance

These are internal fast paths only — encoded output bytes and decoded values are unchanged.

- **Page-granular parallel encode in the row-group finalize** (`src/writer/row_group_writer.c`, `src/writer/page_tasks.h`): the OpenMP finalize scheduled one task per column, so a three-column row group used three threads however many cores there were, and the wall time was bounded by the slowest column (the poorly compressible INT64 `id` column in the benchmark). For flat fixed-stride deferred columns (REQUIRED; INT32/INT64/FLOAT/DOUBLE/INT96/FIXED_LEN_BYTE_ARRAY; PLAIN or BYTE_STREAM_SPLIT; no dictionary, bloom filter or page index) the page boundaries the eager encoder would choose depend only on the value count, so the stash is now cut into pages up front and every page — encode, statistics, BYTE_STREAM_SPLIT transpose, CRC and compression — is one task, dynamically balanced across all OpenMP threads with per-thread scratch page writers; each column then stitches its pages together in order. Columns that do not qualify (nullable, BYTE_ARRAY, BOOLEAN, dictionary, DELTA encodings, bloom filter) still run as one task each and are scheduled first. Output is byte-identical to the serial path (same values per page, same code per page), asserted chunk-for-chunk against one-column files by `tests/test_parallel_write.c` for every codec, Data Page V2, `write_batch_size` and `max_rows_per_page`.
- **SIMD BYTE_STREAM_SPLIT transpose at page finalize** (`apply_byte_stream_split()`, `src/writer/page_writer.c`): the per-page transpose introduced with the multi-call BYTE_STREAM_SPLIT fix was a scalar byte loop with a multiply per byte plus a 1 MB `malloc`/`free` per page, and it sits on the default path of every compressed FLOAT/DOUBLE column — in the 10M-row benchmark it cost as much CPU as the LZ4 compression of the same column. 4- and 8-byte values now go through the dispatched transposers (NEON/SSE/AVX2, the same kernels the encoding module already used before the fix), other widths through a plane-major scalar loop, and the planes land in the page writer's reusable staging buffer, which is then swapped in as the values buffer.
- **Deferred nullable replay counts non-nulls with the SIMD helper** (`encode_batch_eager()`, `src/writer/column_writer.c`): the per-chunk dense-cursor advance scanned the definition levels in a scalar loop; it now uses `carquet_dispatch_count_non_nulls()` like the rest of the writer.

Measured together with `benchmark/run_benchmark.py` (10M rows, INT64/DOUBLE/INT32, 10 row groups, Apple M3, trimmed median of 11; `benchmark/bench_0.7.1_darwin_arm64_20261008.json`): write time snappy 129 → 65 ms, zstd (level 1) 150 → 71 ms, lz4 128 → 63 ms versus the 0.6.0 numbers in the README, i.e. 3.9-4.9x faster than Arrow C++ 24.0.0 instead of 1.9-2.2x. Uncompressed writes are bounded by the kernel page-cache copy and stay at ~65 ms (best-of-N runs show ~55 ms; the figure is sensitive to disk write-back on this machine). Read times are unchanged (the reader already decompressed every column of every row group in parallel).
- **Arrow write: bulk fast path for flat fixed-width columns** (`src/writer/arrow_c_import.c`): `carquet_writer_write_arrow()` shredded every column one row at a time through the generic Dremel recursion — a function call, a capacity check, and a 4/8-byte `memcpy` per element. Top-level, non-nested, non-dictionary, fixed-width primitive leaves (the common flat-table case) now take a `shred_flat_fast()` path: a single bulk `memcpy` of the contiguous Arrow values buffer plus a one-pass definition-level fill when all rows are present, or a dense present-only copy when nulls are mixed in. Nested / dictionary / boolean / byte-array leaves fall back to the generic shredder unchanged.
- **PLAIN `BYTE_ARRAY` encode: one reservation per call** (`src/encoding/plain.c`): `carquet_encode_plain_byte_array()` did two buffer appends (length prefix, then payload) — each re-checking capacity — per value. It now sums the total size, grows the buffer once, and writes through a raw advancing pointer.
- **Bit-packing encode rewritten as a single-pass accumulator** (`src/core/bitpack.c`): `carquet_bitpack8_32` replaced its per-value variable-length byte loop (and the preceding output-zeroing `memset`) with one 64-bit accumulator pass that flushes whole bytes. Runs on every dictionary-index and RLE bit-packed-level write.
- **Bit-unpacking decode: per-group dispatch hoisted** (`src/core/bitpack.c`): `carquet_bitunpack_32` resolved the SIMD/specialized kernel once per 8-value group; it now resolves it once per run (and calls the general 9-32-bit unpack directly, skipping dispatch entirely for those widths). Hot for definition/repetition-level and >256-entry dictionary-index decode.
- **Nullable read: SIMD non-null count** (`src/reader/batch_reader.c`): the row-align expansion pass counted non-null slots with a scalar sweep over the definition-level array; it now uses the SIMD-dispatched `carquet_dispatch_count_non_nulls` already used on the write side.

### Packaging & Build

- **carquet now cooperates with a parent project that builds its own zstd / zlib / lz4** ([#23](https://github.com/Vitruves/carquet/issues/23)). Two changes, both only relevant when carquet is added with `add_subdirectory()` / `FetchContent`. First, when carquet is about to fetch one of the three libraries and the enclosing project already builds it under the target name that fetch would use (`libzstd_static`, `zlibstatic`, `lz4_static`), that target is reused. Previously carquet fetched a second copy and the configure step died with "add_library cannot create target ... because another target with the same name already exists" — the normal outcome on a machine with no system copies, such as Windows. This needs no configuration. Second, `CARQUET_ZSTD_TARGET` / `CARQUET_ZLIB_TARGET` / `CARQUET_LZ4_TARGET` name the exact target to link, for a project that wants its own build rather than the system one or that builds several variants (a static and a shared zlib): `set(CARQUET_ZLIB_TARGET zlibstatic)` before adding carquet, or `-DCARQUET_ZLIB_TARGET=zlib` on the command line. A named target is linked as is, with no `find_package`, pkg-config or `FetchContent` for that library, and a name that is not a target is a configure error rather than a silent fallback. Such a target may be imported or built in-tree, static or shared, and must carry its include directories as a usage requirement (the stock CMake targets of zlib 1.3.1, zstd 1.5.6 and lz4 1.10.0 do). Standalone builds are unchanged. Documented under "Using Your Own zstd / zlib / lz4" in the README.
- **`CARQUET_BUNDLE_DEPS=ON` is now honoured when carquet is built inside another project.** With bundling on, carquet does not search for zstd / zlib / lz4 at all, but it still read `ZSTD_FOUND` / `ZLIB_FOUND` / `lz4_FOUND` — so a value left in scope by the enclosing project's own `find_package` calls, or cached by an earlier non-bundled configure of the same build directory, was taken for carquet's own result and the system library was linked instead of the bundled one. Those flags are now cleared on the bundling path. Found while reviewing [#29](https://github.com/Vitruves/carquet/issues/29); the `lz4_FOUND` spelling questioned there is correct (it is the variable `find_package(lz4 CONFIG)` sets) and now carries a comment saying so.

## v0.7.0

Additive API release: the Arrow C Data Interface bridge (zero-dependency export/import of `ArrowSchema`/`ArrowArray`) with **arbitrary-depth nested read and write** (generic Dremel shredding/reassembly of struct/list/large-list/map at any depth), Arrow-style per-field metadata (variable labels/descriptions), nested `ARROW:schema` emission and type-refinement read-back, and automatic bloom-filter / statistics row-group pruning in the batch reader (now composed with repeated-column projections). This release also lands a batch of **Parquet-conformance fixes** (see the dedicated section below) that bring the on-wire output in line with the spec and Arrow C++/parquet-mr — several of these change default output bytes for the affected columns (SizeStatistics / ColumnIndex histograms, `distinct_count`, the OffsetIndex field-2 correction) and one changes a codec on the wire (`CARQUET_COMPRESSION_LZ4` now emits Hadoop-framed codec 5 instead of aliasing to `LZ4_RAW`). No breaking API/ABI change. Aside from those conformance changes, default output bytes are unchanged, with one exception: writing **nullable `BYTE_ARRAY` columns** may now pick slightly different automatic row-group boundaries — the internal batch-size estimate previously read past the packed value array for such columns (undefined behaviour), and correcting it changes the estimated byte total.

### API

- **Arbitrary-depth nested Arrow interchange** — the Arrow C Data Interface bridge is no longer flat-only. `carquet_writer_write_arrow()` now runs a generic Dremel record-shredder that walks the Arrow `ArrowArray` tree and the writer's leaf columns in lockstep, emitting each leaf's repetition/definition levels and dense values — handling `struct`, `list`, `large_list` and `map` composed to any depth. The new **`carquet_reader_read_arrow()`** is its inverse: it reads one row group's leaf `(rep, def, value)` streams and reassembles the full nested `ArrowArray` tree (offsets + validity at every level). `carquet_arrow_import_schema()` and `carquet_arrow_export_schema()` map nested Arrow ↔ Parquet types recursively (Parquet 3-level LIST ↔ Arrow `List`, Parquet MAP ↔ Arrow `Map<struct<key,value>>`, group ↔ `Struct`). Round-trip verified against PyArrow across `list<list<...>>`, `list<struct>`, `struct<...,list>`, `map<k,list<v>>`, and depth-3 nesting. Deeper-than-single-level cases that previously returned `CARQUET_ERROR_NOT_IMPLEMENTED` are now fully supported.
- **Zero-copy batch export handles single-level LIST / MAP — `carquet_arrow_export_batch()`**: the C-Data-Interface batch export is no longer flat-only. It now walks the top-level schema fields and expands a single-level `LIST<T>` into an Arrow `List` child (offsets + list-level validity + flattened element child) and a `MAP<K,V>` into an Arrow `Map` child (`entries` struct of key/value), consuming the corresponding leaf columns from the row batch via `carquet_row_batch_column_list()`. Flat schemas are byte-identical to before. STRUCT and deeper-than-single-level nesting still return `CARQUET_ERROR_NOT_IMPLEMENTED` here — those are served by `carquet_reader_read_arrow()`, which reassembles arbitrarily nested arrays directly from a row group.
- **Composable nested-schema builders — `carquet_schema_add_list_group()` / `carquet_schema_add_map_group()`**: return the inner REPEATED group of a LIST / MAP container so the caller can attach an arbitrary element / key / value subtree (leaf, struct, or another list/map), enabling `LIST<LIST<...>>`, `LIST<STRUCT<...>>`, `MAP<K, LIST<V>>`, etc. `carquet_schema_add_list()` / `carquet_schema_add_map()` remain the primitive-element convenience forms.
- **Page filters compose with repeated-column projections**: when a page filter is installed and the projection includes a repeated (`max_rep_level >= 1`) column, the batch reader now prunes whole row groups whose statistics prove no row matches (instead of silently ignoring the filter). Sub-row-group page ranges are still not applied to repeated leaves — matching row groups are read in full — because a repeated leaf's slot count does not align with logical row ranges.
- **Nested write helper (auto-shredding) — `carquet_writer_write_list_column()`**: writes a single-level repeated (LIST / MAP) leaf column directly from Arrow-style `int32` offsets and validity bitmaps, computing the definition/repetition levels internally instead of requiring the caller to precompute them. It is the write-side inverse of `carquet_row_batch_column_list()` and handles the standard encoding produced by `carquet_schema_add_list()` (`LIST<T>`) and `carquet_schema_add_map()` (`MAP<K,V>` — key and value leaves share the map's entry offsets). Deeper nesting returns `CARQUET_ERROR_NOT_IMPLEMENTED`; malformed offsets / null-into-REQUIRED are rejected with `CARQUET_ERROR_INVALID_ARGUMENT`. The shredded output is byte-identical to a hand-computed `carquet_writer_write_batch()` with the same levels.
- **`ARROW:schema` now emitted for nested schemas**: the footer `ARROW:schema` blob (opt-in via `write_arrow_schema`) is no longer flat-only. The Parquet schema tree is walked recursively and mapped to Arrow Fields, collapsing the levels Arrow does not model — a Parquet 3-level LIST becomes Arrow `List<element>`, a Parquet MAP becomes `Map<entries: struct<key, value>>`, and a plain group becomes a `Struct` — so Arrow readers (PyArrow, Arrow C++) recover the exact nested Arrow type tree. Any element that cannot be faithfully mapped still aborts emission (no blob) so the footer never disagrees with the Parquet schema. Verified round-trip through PyArrow in the interop suite.
- **Read Arrow type refinements from `ARROW:schema` — `carquet_reader_column_arrow_type_refinement()`**: recovers per-leaf Arrow types that the Parquet type system alone cannot express (64-bit-offset `LargeUtf8` / `LargeBinary`), returning a new `carquet_arrow_type_refinement_t` (`NONE` / `LARGE_UTF8` / `LARGE_BINARY` / `LARGE_LIST`). Purely informational — the column's values are read exactly as before. Recovery is best-effort over flat top-level fields and never fails an open.
- **Automatic statistics- and bloom-filter-based row-group pruning in the batch reader**: when page-filter clauses are installed (`carquet_batch_reader_set_page_filter`), the reader now drops whole row groups whose ColumnChunk statistics (min/max/null-count) or bloom filter prove they cannot match — without a user callback and without needing a page index. For equality/`IN` clauses the column's bloom filter is consulted (dropping row groups whose values are provably absent even when they fall inside the min/max range). This is purely additive: it can only skip provably-empty row groups, and page-level range filtering is unchanged.

- **Arrow C Data Interface bridge** (`ArrowSchema` / `ArrowArray`): the standard, zero-copy bridge to the Arrow ecosystem (PyArrow, DuckDB, nanoarrow, ...), defined inline in `carquet.h` behind the usual `ARROW_C_DATA_INTERFACE` guard so it coexists with a real Arrow `abi.h`. Four new entry points, scoped to flat (non-nested) columns: `carquet_arrow_export_schema()` and `carquet_arrow_export_batch()` produce owned Arrow structs from a Carquet schema / row batch (each buffer is an independent copy, valid after the source batch is freed, released via the standard `release` callback); `carquet_arrow_import_schema()` builds a Carquet schema from an Arrow schema, and `carquet_writer_write_arrow()` writes an Arrow struct array to a writer (converting validity bitmaps to definition levels and compacting values). Import follows Arrow "move" semantics — the passed structs are consumed. Boolean bit-packing, UTF8/binary offsets, and fixed-size binary are all handled.
- **Nested (single-level LIST) reconstruction in the batch reader**: repeated columns (`max_rep_level == 1` — a `LIST<T>` element or a `MAP` key/value leaf) are now materialized into Arrow's `List<T>` layout by the batch reader, exposed through the new `carquet_row_batch_column_list()` accessor (offsets + flattened child array + child validity + list-level validity). Previously the batch reader passed `NULL` for repetition levels and misaligned any repeated column; it now reads a whole row group per batch for such projections and reconstructs offsets/validity from the def/rep levels. The flat accessor `carquet_row_batch_column()` now rejects list columns (returns `CARQUET_ERROR_INVALID_ARGUMENT`) rather than silently returning the flattened child. (Arbitrary-depth nesting `max_rep_level > 1` and page-filter composition with repeated projections landed later in this same release — see above.)
- **New `carquet_writer_num_columns()`** accessor (mirrors `carquet_reader_num_columns()`), used by the Arrow write path to validate array shape.
- **Per-field metadata (variable labels/descriptions) via `ARROW:schema`**: a new `carquet_schema_set_field_metadata(schema, element_index, key, value)` attaches Arrow-style `Field.custom_metadata` (e.g. `Label` → `"Sex of Respondent"`) to a schema field. When the `write_arrow_schema` writer option is enabled, the pairs are emitted into the file-level `ARROW:schema` footer blob — the correct, reader-agnostic home for schema-level annotations — so any Arrow-compatible reader (PyArrow, Parquet viewers) surfaces them automatically as field metadata. This is deliberately *not* written to `ColumnMetaData.key_value_metadata`, which repeats per row group and is wrong for file-level annotations. Setting the same key twice replaces the value; distinct keys accumulate. Only flat top-level fields are emitted, matching the existing `ARROW:schema` writer.
- **Read per-field metadata back**: a new bounds-checked FlatBuffer *reader* recovers `Field.custom_metadata` from the `ARROW:schema` blob on open (carquet's own output or PyArrow's / Arrow C++'s). Three new accessors expose it per leaf column: `carquet_reader_column_num_metadata()`, `carquet_reader_column_get_metadata()`, and `carquet_reader_column_find_metadata(reader, column, "Label")`. Parsing is best-effort — a malformed or absent blob simply yields zero entries and never fails the open.

### Parquet conformance (Parquet 2.9 / spec fixes)

These fix carquet's on-wire output to match the Parquet spec and Arrow C++/parquet-mr. Several change **default output bytes** for affected columns (all backward-compatible additions or corrections of malformed fields — noted per bullet).

- **Hadoop-framed LZ4 (codec 5)** — `CARQUET_COMPRESSION_LZ4` and `CARQUET_COMPRESSION_LZ4_RAW` are now **distinct** Parquet codecs: codec 5 is the deprecated Hadoop-framed LZ4 (length-prefixed blocks), codec 7 is raw LZ4 blocks. Legacy Spark/Hadoop LZ4 files (codec 5) now open, and both codecs round-trip. **Wire change**: requesting `CARQUET_COMPRESSION_LZ4` previously produced codec-7 (`LZ4_RAW`) bytes via an internal alias; it now produces codec-5 Hadoop-framed bytes. Use `CARQUET_COMPRESSION_LZ4_RAW` for the previous behaviour.
- **SizeStatistics (Parquet 2.9)** — `ColumnMetaData.size_statistics` (field 16) is now written and read: `unencoded_byte_array_data_bytes` (BYTE_ARRAY columns) plus `definition_level_histogram` / `repetition_level_histogram`, computed per page and summed per chunk. **Default-bytes change**: emitted for nullable, nested/repeated, and BYTE_ARRAY columns (where it carries information); flat required non-BYTE_ARRAY columns are byte-identical to before. Gated by the existing write-statistics option.
- **ColumnIndex level histograms (Parquet 2.9)** — the page index now writes per-page `repetition_level_histograms` / `definition_level_histograms` (fields 6/7) for repeated / nullable columns. **Default-bytes change** for page-index files with such columns.
- **OffsetIndex field 2 corrected** — now writes the spec's `unencoded_byte_array_data_bytes` (`list<i64>`, BYTE_ARRAY only) instead of a non-standard `uncompressed_page_sizes` (`list<i32>`). **Wire change** for page-index files (the previous field was not spec-conformant and was ignored by other readers).
- **RLE as a value encoding for BOOLEAN** — `carquet_writer_set_column_encoding(w, col, CARQUET_ENCODING_RLE)` now writes RLE BOOLEAN data pages (4-byte length prefix + bit-width-1 hybrid, matching parquet-mr), and the reader decodes them (previously `INVALID_ENCODING`). Opt-in; PLAIN remains the default.
- **Dictionary encoding for `FIXED_LEN_BYTE_ARRAY`** — FLBA columns now honour a requested dictionary encoding (fixed-width dictionary) instead of silently falling back to PLAIN.
- **`Statistics.distinct_count` (write)** — now populated exactly (from the dictionary) for dictionary-encoded chunks. **Default-bytes change**: dictionary columns gain a `distinct_count` in their Statistics.
- **`is_min/max_value_exact`** — the live writer already sets these to `false` on a truncated BYTE_ARRAY min/max; the unused `metadata/statistics.c` builder that hardcoded `true` was **removed** (dead code, no callers, no ABI impact).
- **Compressed `BloomFilterHeader` (read)** — the header's `compression` union is parsed; a header declaring anything other than `UNCOMPRESSED` is now rejected with `CARQUET_ERROR_UNSUPPORTED_CODEC` instead of feeding the bytes to the filter reader as if raw.
- **`column_orders` preserved on read** — each `ColumnOrder` union tag is retained (`parquet_file_metadata.column_order_types`) rather than only the count.

### Security / Bug Fixes

- **Fix a heap over-read in the Arrow C Data Interface format-string parser** (found by fuzzing): `parse_arrow_format()` tested `fmt[3]` for a timestamp format (`"ts<unit>:<tz>"`) before confirming `fmt[2]` was non-NUL, so a truncated `"ts"` (whose NUL terminator sits at index 2) read one byte past the string. ## v0.6.1

Security hardening release from a full library audit, plus one small, focused API addition. No breaking API/ABI change; existing symbols and default output bytes are unchanged.

### Packaging & Build

- **Prebuilt binaries on every release**: a new `.github/workflows/release.yml` attaches self-contained static libraries to each `vX.Y.Z` GitHub Release for macOS arm64, Linux x86-64/arm64, and Windows x64 — no source build required. Each holds `include/carquet/`, `lib/libcarquet.a` with **zstd/zlib/lz4 bundled in**, and the CMake package config; consume via `find_package(carquet)` or `-Ilib/include -Llib -lcarquet`. Built on the oldest runner (low glibc floor) and without LTO/OpenMP so it links from any consumer toolchain.
- **New `CARQUET_BUNDLE_DEPS` CMake option** (default `OFF`): forces fetch + static-bundle of zstd/zlib/lz4 for a portable self-contained archive; the normal build still prefers system libraries.
- **`find_package(carquet)` now works from an install tree**: `carquetConfig.cmake` is now installed (previously only `carquetTargets.cmake` shipped), static builds export their bundled compression archives in the install link interface (previously dropped → undefined zstd/zlib/lz4 symbols), and the config resolves `Threads`/`OpenMP` via `find_dependency`.
- **`xmake.lua` build alongside CMake**: carquet can now also be built with [xmake](https://xmake.io), mirroring the same options and test wiring; CMake remains the reference build.

### API

- **New `carquet_column_read_batch_ex()` for detailed read-error reporting** (small, additive, ABI-compatible): `carquet_column_read_batch()` collapsed four distinct failure conditions (invalid `max_values`, unknown physical type, scratch-buffer allocation failure, and page-read failure) onto the single return value `-1`, and could not signal a page-read failure that truncated a batch after some values had already been read — it returned the partial count, indistinguishable from a clean end-of-column short read. The new variant takes a trailing `carquet_error_t*` out-parameter that carries a distinct status code (and message) per failure and, on a mid-batch truncation, reports the error while still returning the salvaged count so the caller can both use the partial data and detect that it is incomplete. `carquet_column_read_batch()` is now a thin wrapper over the new function with identical behavior — no existing call site changes and no ABI break.

### Security / Bug Fixes

- **Reject columns whose chunk-metadata physical type disagrees with the schema** (heap buffer overflow, found by fuzzing): the value width is derived from the schema on the batch-reader path but from the column-chunk metadata on the page-reader path. A crafted file that declared, say, `INT32` in the schema (4 bytes/value) but `BYTE_ARRAY` in the chunk metadata (`sizeof(carquet_byte_array_t)`/value) made the page decode write past the batch reader's output buffer. The column reader now validates the two types match at construction and rejects the file with `CARQUET_ERROR_INVALID_METADATA` when they do not.
- **Reject malformed dictionary pages that could read out of bounds**: a crafted BYTE_ARRAY dictionary with an oversized entry-length prefix could slip past a size check and expose out-of-bounds bytes when the value was read. Such pages are now rejected.
- **Reject truncated PLAIN pages on the memory-mapped read path**: a crafted page header could claim more values than its payload actually held, causing an out-of-bounds read when the values were copied out (found by fuzzing). The zero-copy read path now validates the payload size before use, matching the buffered path.
- **Guard against denial-of-service from crafted footers**: a malformed schema declaring a huge child count could stall the reader in a near-endless loop; oversized footer-length fields on very large files could mis-parse. Both are now bounded and rejected cleanly.
- **Guard length-array allocations in DELTA byte-array decoders**: value counts from the page header are now range-checked before allocating, preventing a size overflow on 32-bit platforms.
- **Clear stale error on memory-map fallback**: when a file opened successfully via the buffered fallback after a memory-map attempt failed, a leftover error was left set on the caller's error object. The error is now cleared on success.
- **Avoid unaligned float/double reads in BYTE_STREAM_SPLIT for FIXED_LEN_BYTE_ARRAY**: the 4-/8-byte BYTE_STREAM_SPLIT fast paths reinterpreted the value buffer as `float*`/`double*`. For FLBA(4)/FLBA(8) that buffer carries no alignment guarantee, so the cast was undefined behavior and could `SIGBUS` on strict-alignment targets. The fast path is now taken only when the buffer is naturally aligned; otherwise the generic byte transpose runs. Output bytes are identical (the aligned FLOAT/DOUBLE paths are unaffected).
- **Bounds-check the BYTE_ARRAY dictionary fallback scan** (defense-in-depth): the unreachable fallback that scans a dictionary entry-by-entry computed `4 + len` in 32-bit arithmetic with no per-entry bound, so a wrapped length could have walked past the dictionary buffer. The scan is now `size_t`-widened and bounded against the dictionary size. This path is not reachable by current readers (the offset table is always built); the guard prevents future misuse.

### Interoperability

- **Read DELTA_BINARY_PACKED pages from any conformant writer**: the decoder previously accepted only the 128-values-per-block / 4-mini-block layout that carquet itself writes and rejected other spec-valid layouts (e.g. block sizes of 256 or 512). It now accepts any block size that follows the Parquet spec, so DELTA-encoded columns written by Arrow, parquet-mr and others read correctly.
- **Keep predicate pushdown enabled for empty-string min/max stats**: presence of a column's `min_value`/`max_value` is now tracked from the Thrift field itself rather than inferred from its length, so a foreign file whose BYTE_ARRAY/STRING minimum is the empty string is no longer treated as having no statistics. Previously such a column silently disabled row-group pruning (a missed optimization, never a wrong result). Reader-side only; carquet's own writer output is unchanged.

### Performance

- **Faster decode of wide bit-packed values (~1.8–2.0× on Apple Silicon)**: the general bit-unpacking path for widths of 9–32 bits — used to decode dictionary indices for dictionaries with more than 256 entries, and wide RLE/DELTA runs — was rewritten from a byte-at-a-time loop into a branchless load-shift-mask. Output is byte-for-byte identical.

### Robustness

- **Serialize lazy SIMD dispatch initialization**: the runtime SIMD function table is now populated under a lock (matching the library's other lazy init), removing a data race when the first SIMD use happens concurrently across threads (e.g. parallel column reads).
- **Prevent SIMD instructions from leaking into portable code paths under LTO** (x86 builds): the AVX/AVX-512 translation units are compiled without LTO so ISA-specific code cannot be inlined into baseline paths that run before the runtime CPU check. `CARQUET_NATIVE_ARCH` is now documented as producing a host-only, non-portable binary.
- **Remove a data race on the parallel column-read error flag**: the OpenMP column-read loop shared a single `read_error` flag written by every thread. Each column now writes its own error slot, reduced after the parallel region, so there is no shared write (the previous torn-write was benign in practice but a genuine data race).

## v0.6.0

Source-compatible additive release. Closes the two remaining "small" Arrow-parity gaps. ABI break only in the strict sense that `carquet_writer_options_t` gains a trailing `int32_t` field; existing code that goes through `carquet_writer_options_init()` is unaffected and default output bytes are unchanged.

### New Features

- **Page-level filtering (predicate pushdown to data pages)**: new `carquet_batch_reader_set_page_filter(reader, clauses, count)` attaches a conjunction of clauses to the batch reader. Each clause is `(column_index, op, value)`; supported ops are `EQ` / `NE` / `LT` / `LE` / `GT` / `GE` / `RANGE` / `IN` / `IS_NULL` / `IS_NOT_NULL`. The filter is evaluated against the column index, and only pages whose min/max range could match are decompressed and decoded. Predicate columns do not need to be in the projection — when they are not, only their column + offset index is read, never the data pages. Clauses AND'd across different columns are supported, with per-row-group row range intersection. Both sequential and pipeline batch-reader paths are filter-aware: the pipeline pre-reads only matching pages into the slot buffers in parallel. Diagnostic `carquet_batch_reader_rows_skipped()` reports the running pruned-row count. `INT96` predicates are rejected (no defined sort order); a clause against a column written without `write_page_index` surfaces `CARQUET_ERROR_PAGE_INDEX_REQUIRED` on the next `next()` call. New error code `CARQUET_ERROR_PAGE_INDEX_REQUIRED`, new types `carquet_filter_op_t` / `carquet_filter_clause_t`, implementation in `src/reader/page_filter.{c,h}` with a new column reader `seek_to_data_page` primitive in `src/reader/page_reader.c`.
- **Append row groups to existing files**: new `carquet_writer_open_append(path, schema, options, error)` opens an existing Parquet file with read+write access, parses the trailing footer, validates that the supplied schema matches the file's leaf columns (count / name / physical type / repetition), and returns a writer positioned at the byte just before the existing footer. Subsequent `write_batch` / `new_row_group` calls add row groups; `close()` writes a fresh footer listing the existing row groups followed by the new ones. Existing bloom filters and page indexes are preserved (they sit between row group data and the original footer, which is the region the writer overwrites). Key-value metadata is carried over; further `add_metadata` calls accumulate. Schema mismatch surfaces as `CARQUET_ERROR_INVALID_SCHEMA` and leaves the file unmodified. This enables streaming ingestion, log accumulation, and periodic-snapshot workflows without read-then-rewrite.
- **CLI: row-predicate filtering via `--filter`**: `carquet cat`, `count`, `head`, and `export` accept `-p / --filter EXPR` to push a row predicate down to the page level. Grammar: `column OP value [AND column OP value]...`, with `OP` ∈ {`=`, `==`, `!=`, `<>`, `<`, `<=`, `>`, `>=`}, plus `column IS NULL` and `column IS NOT NULL`. Values are signed numbers, single-quoted strings (with `''` escape), or `TRUE`/`FALSE`; the literal is parsed against the column's physical type. Pages whose column-index min/max cannot match the predicate are skipped without decompression. `tail` and `sample` reject `--filter` with a helpful workaround hint (`cat -p ... | tail`, `cat -p ... | shuf | head`) since they would require materializing every matching row. When the file lacks a page index for a referenced column, the CLI surfaces a clear "re-write with write_page_index = true" message instead of returning zero rows. Internally the CLI builds a `carquet_filter_clause_t[]` and routes filtered reads through the batch reader; unfiltered reads keep their existing column-reader fast path so behavior on plain `cat`/`count` is byte-for-byte unchanged.
- **CLI: `info` now surfaces page-index and sort-order metadata**: when at least one column has a page index, `info` prints a per-column table with the page count and the column-index `boundary_order` (`UNORDERED` / `ASCENDING` / `DESCENDING`); when the file's row groups carry `sorting_columns`, `info` prints a sort-order section listing each declared sort column with its direction and NULLs placement. Both sections are omitted when the metadata is absent, so output on existing files without those structures is unchanged.
- **CLI: `INTERVAL` logical type displayed correctly**: schema/info/stat output now annotates `FIXED_LEN_BYTE_ARRAY(12)` columns carrying the `INTERVAL` annotation as `INTERVAL` instead of falling back to the bare physical type. Affects display only; on-disk format is unchanged.
- **Custom compression codec registration**: new public API `carquet_register_codec(codec, impl)` + `carquet_custom_codec_t` (compress / decompress / compress_bound + opaque `user_data`). A registered codec takes priority over the built-in for that slot in both the reader (`carquet_decompress_page`) and writer (`compress_data`), so users can swap in a hardware-accelerated implementation or fill the `LZO` / `BROTLI` slots that carquet has no built-in for. Passing `impl = NULL` unregisters; registering against `UNCOMPRESSED` is rejected (that path has a no-copy fast lane that must not be intercepted). Registrations are process-wide and not safe to mutate concurrently with reader/writer activity. Implementation: `src/compression/custom.{h,c}`.
- **Per-column page-size override**: new `carquet_writer_set_column_page_size(writer, column_index, bytes)` overrides `options.page_size` for one column. Useful when some columns benefit from smaller pages (finer page-index pruning) and others from larger pages (lower per-page header overhead). Mirrors the existing per-column compression/encoding override pattern.
- **Configurable BYTE_ARRAY statistics truncation cap**: new `carquet_writer_set_max_statistics_size(writer, bytes)` controls the byte cap for variable-length min/max stored in column statistics (default `32`, matching Arrow and the Parquet spec recommendation). The existing truncation logic — min stored as leading prefix, max stored as prefix-then-increment, all-`0xFF` max suppressed rather than emitted as an invalid bound — is unchanged; only the threshold becomes tunable. The `is_min/max_value_exact` flags continue to reflect whether the stored value equals the actual column min/max.
- **File format version control**: new `carquet_writer_options_t.file_format_version` (default `2`) writes the requested value into `FileMetaData.version` in the footer. Set to `1` for the rare older readers that reject version-2 files; any other value is treated as `2`. Independent of `data_page_version`.

### Bug Fixes

- **Nullable batched-write value mis-indexing**: when `carquet_writer_write_batch` was called on an OPTIONAL column with a batch large enough to be split into multiple page chunks (i.e. larger than `write_batch_size` or the page-size-derived heuristic), the eager encode path indexed the dense values array by the logical row offset instead of the cumulative non-null count, so chunks beyond the first read values from the wrong rows of the dense array. The values array is now advanced by the per-chunk non-null count as the spec requires. Fixes silent corruption of OPTIONAL columns whose writer batches were larger than one page worth of rows.
- **`codegen` aborting with "buffer overflow detected" in Release builds**: `cmd_codegen_read` resolved the input path with `realpath()` into a 1024-byte buffer, but `realpath()` requires a buffer of at least `PATH_MAX` (4096 on Linux). On distros that enable `_FORTIFY_SOURCE` for optimized builds (e.g. Ubuntu's GCC at `-O2`), `__realpath_chk` aborts unconditionally because the buffer is smaller than `PATH_MAX`, so `carquet codegen -f file.parquet` died before producing output; unfortified Debug builds skip the check and worked. The buffer is now sized to `PATH_MAX`/`_MAX_PATH` (and the escaped-path buffer widened to match), in `src/cli/codegen_read.c`.
- **Page index offsets now absolute**: `OffsetIndex.PageLocation.offset` is now an absolute file offset per the Parquet spec. Previously, the writer recorded relative-within-column offsets because eager page flushes ran before the row-group writer set the column's absolute file position. The column writer now stores per-column relative offsets while flushing and applies the column file offset as a single shift at finalize time. Downstream readers that consume `OffsetIndex` (now including carquet's own page filter) get spec-compliant offsets.
- **Malformed Data Page V1 levels when a page spanned multiple value chunks**: for an OPTIONAL or repeated column whose page accumulated more than one `add_values` chunk before a byte-size-triggered flush (the common case with a small `page_size`), each chunk's definition/repetition levels were emitted with their own 4-byte RLE length prefix, so the page's level section became several concatenated `[len][rle]` runs while the page header advertised a single level stream. carquet's own reader tolerated this, but PyArrow (`Number of decoded rep / def levels do not match num_values in page header`) and DuckDB (`Out of buffer`) rejected such files. Levels are now stored as raw RLE with the single V1 length prefix written once at page assembly, so multi-chunk pages are spec-conformant. Output for single-chunk pages (the default for large pages) is byte-identical; row-count-split pages (`max_rows_per_page`) and Data Page V2 were already correct. Found by the new `zstd+multipage` interop variant.

### Performance

- **NEON BYTE_STREAM_SPLIT for double rewritten with structure load/stores**: the AArch64 transpose for `double` columns (the default encoding for floats under compression) now uses `vld4q_u16` / `vst4q_u16` instead of `vqtbl` table lookups. `LD4`/`ST4` de-interleave at the load-store unit and far outpace the two-register `vqtbl2q` gather on Apple Silicon. Measured on M3: double **decode +47–69%** (read path) and encode well above the old table path, byte-exact identical output. `float` BSS stays on the auto-vectorized scalar path — benchmarked faster than both `vqtbl` and `vld4` there, where the latter regresses small in-cache decode. Implementation in `src/simd/arm/neon_ops.c`, wiring in `src/simd/dispatch.c`.

### Testing

- **Fuzzing seeded from the Apache `parquet-testing` corpus**: the fuzz harness (`fuzz/fetch_corpus.sh` + `run_fuzzer.py`) now pulls Apache's official `parquet-testing` data files — real-world files spanning varied types, encodings, codecs, nested/nullable, multi-row-group and page-indexed layouts, plus the intentionally malformed inputs under `bad_data/` — and uses them as seeds for the reader and page-filter targets. Fuzzing carquet directly against the canonical Parquet reference corpus (rather than only self-generated seeds) is independent confirmation that carquet correctly parses spec-conformant files and rejects malformed ones. New targets `fuzz_append` and `fuzz_page_filter` extend coverage to the append and page-filter paths.

### Compatibility

**Not binary-compatible with v0.4.4 — recompile against the new headers; do not merely relink.** Source compatibility is preserved (existing code compiles unchanged: every new option-struct field defaults to the previous behavior, and the `created_by` array decays to `char*` where the old `const char*` was read), but the ABI changed:

- **Enlarged caller-allocated public structs.** `carquet_writer_options_t` gained `write_arrow_schema`, `data_page_version`, `max_rows_per_page`, `coerce_timestamps`, `coerce_timestamp_unit`, `allow_timestamp_truncation`, and `write_batch_size`; `carquet_batch_reader_config_t` and the bloom-filter options also grew. These structs are allocated **by value** by callers, so their `sizeof` changing means a v0.4.4 binary relinked against v0.4.5 (or vice versa) without recompiling reads/writes them at the wrong offsets. This affects real existing consumers and is the primary reason this is an ABI break.
- **New enumerator** `CARQUET_LOGICAL_INTERVAL` added to `carquet_logical_type_id_t`.
- **`carquet_file_info_t` layout change**: `created_by` changed from `const char*` to inline `char created_by[CARQUET_CREATED_BY_MAX]` (256), changing the struct's size. Listed for completeness only: its sole consumer, `carquet_get_file_info()`, had no definition before v0.4.5 (it never linked), so no existing binary or even compilable program can depend on the old layout — this part breaks nothing in practice.

### Bug Fixes

- **Implemented missing public API functions**: `carquet_reader_open_file()`, `carquet_get_file_info()`, `carquet_validate_file()`, `carquet_set_allocator()`, and `carquet_get_allocator()` were declared in `carquet.h` but had no definitions, so any program calling them failed at link time. They are now implemented. `carquet_reader_open_file()` reads from a caller-owned `FILE*` (carquet does not take ownership or close it). `carquet_validate_file()` does structural validation **and** streams every row group/column/page with checksum verification enabled, so CRC, decompression, and decode errors are all surfaced rather than a footer-only check.
- **Custom allocator is now actually used**: `carquet_set_allocator()` previously stored the allocator but the library kept allocating through libc, silently ignoring it. Every heap allocation in the library now routes through the configured allocator via internal wrappers, and `carquet_get_allocator()` returns the active one (libc by default). Scratch memory owned by zlib/zstd is unaffected. Verified ASan/UBSan-clean and allocation-balanced across the full suite.
- **Predicate-pushdown comparisons fixed**: row-group statistics filtering read `BOOLEAN` stats with the 4-byte `INT32` comparator (a 3-byte out-of-bounds read of the 1-byte stat), compared unsigned (`UINT32`/`UINT64` via logical or legacy `ConvertedType`) columns with signed ordering (false negatives for large values), and ordered `FLOAT16` stats byte-lexicographically instead of numerically. Comparisons are now type-correct, unsigned-aware, FLOAT16-numeric, and read stat bytes via memcpy (no unaligned access); a stat whose width does not match the column type is treated as indeterminate so the row group is conservatively kept.
- **x86 SIMD dispatch hardened**: CPU feature detection now checks `OSXSAVE` + `XGETBV`/`XCR0` before selecting AVX/AVX2 (the OS must have enabled YMM state) and additionally requires opmask/ZMM state plus `AVX512BW`+`AVX512VL` before selecting AVX-512 paths (the AVX-512 objects are compiled with BW/VL), preventing `#UD`/`#GP` on machines that advertise but do not fully enable these. The lazy dispatch-table initialization is now acquire/release atomic, closing a first-use data race.
- **Removed a latent bit-unpack buffer-overflow landmine**: the unused `carquet_neon_bitunpack8_32` was documented and named as an 8-value unpacker but dispatched to 32- and 16-value kernels for bit widths 1 and 2. It had no callers (NEON never wired the bit-unpack table), so it could not corrupt memory as shipped, but wiring it like the x86 path would have written 32/16 values into 8-element buffers. It and the now-orphaned pure-scalar `carquet_neon_bitunpack16_2bit` and `carquet_avx2_bitunpack64_1bit` dead kernels were removed.

### Performance

- **Wide SIMD bit-unpacking**: bit-unpacking — used by DELTA decode (`carquet_bitunpack_32`) and by RLE definition/repetition-level decode (`carquet_rle_decode_levels`) — now processes 16 or 32 values per SIMD call for the common bit widths 1/4/8/16 instead of 8 at a time, via a new verified dispatch tier that finally wires the previously dead-but-correct wider kernels (SSE 32×1-bit; AVX2 16×4/8-bit; AVX-512 32×4/8-bit and 16×16-bit; NEON 32×1-bit). Other widths and truncated / output-capped bit-packed runs fall back to the unchanged 8-at-a-time path, so output is bit-identical. A new `test_bitunpack_wide` validates `carquet_bitunpack_32` and the RLE level/all decoders against an independent scalar oracle across every bit width and chunk-boundary count (ASan+UBSan-clean).

### New Features

- **Dictionary page writing (opt-in)**: The writer can emit a real `DICTIONARY_PAGE` (PLAIN-encoded entries) followed by `RLE_DICTIONARY` data pages, with the column chunk's `dictionary_page_offset` set. Enable it per column with `carquet_writer_set_column_encoding(writer, col, CARQUET_ENCODING_RLE_DICTIONARY)`. A column whose dictionary would exceed `dictionary_page_size`, or whose values are effectively all-unique, transparently **falls back to PLAIN** (with an early-abort so high-cardinality columns don't pay to build a dictionary they won't use), and its `ColumnMetaData.encodings` then advertises only the encodings actually used (no spurious `RLE_DICTIONARY`). It is opt-in rather than default because defaulting to it regressed read throughput substantially (notably the zero-copy uncompressed read path) for a size win that is negligible under zstd; the default policy is unchanged from v0.4.4 (PLAIN, with automatic `BYTE_STREAM_SPLIT` for FLOAT/DOUBLE when compression is enabled).
- **Broader per-column writer encodings**: `carquet_writer_set_column_encoding()` now accepts `DELTA_BINARY_PACKED` (`INT32`/`INT64`), `DELTA_LENGTH_BYTE_ARRAY` (`BYTE_ARRAY`), `DELTA_BYTE_ARRAY` (`BYTE_ARRAY` and `FIXED_LEN_BYTE_ARRAY`, per the spec), and `BYTE_STREAM_SPLIT` for `FLOAT`/`DOUBLE`/`INT32`/`INT64`/`FIXED_LEN_BYTE_ARRAY`. This relaxes the stricter-than-necessary rejection added in v0.4.2 to exactly the set the writer can correctly emit.
- **Reader decodes the full opt-in encoding set (symmetry fix)**: the page reader now decodes `DELTA_BINARY_PACKED`, `DELTA_LENGTH_BYTE_ARRAY`, `DELTA_BYTE_ARRAY` (incl. FLBA), and `BYTE_STREAM_SPLIT` for `INT32`/`INT64`/`FIXED_LEN_BYTE_ARRAY` in both V1 and V2 data pages. Previously these could be written but not read back by carquet itself; `DELTA_BYTE_ARRAY` reconstruction reuses the page-retain lifetime so byte-array values stay valid across a multi-page batch (ASAN-clean). A new `test_encoding_roundtrip` test asserts carquet-reads-carquet exactness for every encoding, including a nullable column.
- **`INTERVAL` logical type**: schema/metadata support for the `INTERVAL` annotation (legacy `ConvertedType=INTERVAL`, `FIXED_LEN_BYTE_ARRAY` of length 12); written and read back, and recognized by PyArrow.
- **`sorting_columns` metadata**: The declared sort order of row groups is now written into and read back from row-group metadata instead of being skipped. The order is recorded on every row group (matching PyArrow); the writer records the declaration only and does not sort or verify the data.
- **Per-column bloom NDV/FPP** and **`max_rows_per_page`**: bloom filters can be sized per column; data pages can be flushed by row count in addition to byte size.
- **INT96 writing**: the deprecated `INT96` physical type can now be written (PLAIN, the only valid INT96 encoding). No min/max statistics are produced, matching parquet-cpp's undefined INT96 sort order; PyArrow reads it back as `timestamp[ns]`.
- **Data Page V2 writing (opt-in)**: `carquet_writer_options_t.data_page_version = 2` writes `DATA_PAGE_V2` — repetition/definition levels stored uncompressed and outside the compressed value region, byte lengths carried in `DataPageHeaderV2` (no inline 4-byte level prefix), `num_rows`/`num_nulls` tracked per page. Any value other than 2 keeps the V1 path, which is byte-for-byte unchanged (the level-prefix change and row counting are guarded behind the V2 flag, zero hot-path cost).
- **`ARROW:schema` footer metadata (opt-in)**: with `carquet_writer_options_t.write_arrow_schema = true`, the original Arrow schema is embedded as a base64-encoded encapsulated Arrow IPC Schema message under the `ARROW:schema` key, so Arrow/PyArrow recover Arrow-specific type information losslessly. The Arrow IPC FlatBuffer and base64 are produced by a small hand-written builder (`src/writer/arrow_schema.c`) — no flatbuffers/Arrow dependency. Emitted only for flat schemas and only when the user has not already set that key; nested schemas are left without it rather than written inconsistently.
- **FLOAT16 statistics ordering**: min/max for the `FLOAT16` logical type (`FIXED_LEN_BYTE_ARRAY(2)`) are now computed by the represented floating-point value with NaNs skipped, and a zero min/max is normalized to `-0.0`/`+0.0` (per spec), instead of the incorrect byte-lexicographic ordering. Applied at both the page and column-merge level.
- **Deprecated BIT_PACKED level decoding (read)**: the reader now decodes legacy Data Page V1 files whose definition/repetition levels use the deprecated `BIT_PACKED` encoding (MSB-first, no length prefix), dispatching on the page header's level-encoding fields instead of assuming RLE. New `carquet_decode_bitpacked_levels()` in `core/bitpack`.
- **GeospatialStatistics for GEOMETRY/GEOGRAPHY**: the writer now computes and emits `ColumnMetaData.geospatial_statistics` (field 17): a coordinate bounding box (`xmin/xmax/ymin/ymax`, plus `z`/`m` when present) and the set of ISO-WKB geometry type codes, parsed from the column's WKB values (Point/LineString/Polygon/Multi*/GeometryCollection, both endiannesses, XY/XYZ/XYM/XYZM, EWKB-flag tolerant). New `core/geo_wkb` walker; thrift encode + decode added. Min/max remain suppressed for these types as before.
- **TIMESTAMP coercion**: `carquet_writer_options_t.coerce_timestamps` rescales every `TIMESTAMP` column to `coerce_timestamp_unit` on write and emits the metadata (modern + legacy `ConvertedType`) at that unit, mirroring PyArrow's `coerce_timestamps`; `allow_timestamp_truncation` gates lossy finer→coarser conversion (mirrors `allow_truncated_timestamps`). Off by default.
- **`write_batch_size`**: `carquet_writer_options_t.write_batch_size` caps the internal value-batch size used during column writing (mirrors PyArrow's `write_batch_size`); 0 keeps the automatic page-size-derived heuristic.

### Bug Fixes

- **Statistics are now actually written to Parquet files**: `write_statistics = true` (the default) was silently being ignored — page-level min/max/null counts were never propagated up into the column chunk metadata, so files contained no statistics regardless of the option. Column stats now flow correctly from page → column → row group → file metadata. Existing files written with older versions are unaffected; only the writer was broken.
- **Fixed `carquet stat` CLI segfault on string columns**: The `stat` subcommand crashed when displaying min/max for `BYTE_ARRAY` (string) columns. The bug was latent until statistics actually started being written.
- **Fixed nullable value decoding contract**: Optional columns now consistently use a packed non-null value stream plus definition levels, including `BYTE_ARRAY`, dictionary pages, partial page reads, and generated reader code.
- **Fixed null bitmap polarity**: Batch reader null bitmaps now consistently follow the documented convention: bit set means the value is present.
- **Fixed compressed mmap batch-reader edge cases**: The pipeline no longer drops null information for optional/repeated columns, and intra-column split tasks no longer share mutable column-reader scratch buffers.
- **Rejected unsupported writer encodings**: Per-column encoding overrides now fail fast for encodings the writer cannot actually emit, avoiding mismatched metadata and payloads.

### New Features

- **Statistics for all primitive types**: Min/max/null-count are now tracked for `BOOLEAN`, `BYTE_ARRAY`, and `FIXED_LEN_BYTE_ARRAY` in addition to the numeric types. Byte-array min/max use Parquet-spec lexicographic ordering with min/max truncation at 32 bytes for long values (max is incremented so the stored bound remains a valid upper bound).
- **New CLI commands**:
  - `carquet cat [-n LIMIT] [-s OFFSET] [-c COLS] <file>` — print rows with arbitrary slicing and column filtering. Fills the gap between `head`/`tail` (anchored to start/end) and `sample` (random).
  - `carquet export [--format csv] [-n LIMIT] [-s OFFSET] [-c COLS] <file>` — write rows to stdout as RFC 4180 CSV with the same slicing/filter options. Useful for piping into shell tools or other CSV consumers.
- **Cleaner `carquet stat` output**: columns are now auto-sized to their actual content width instead of fixed 20/30-character cells, so short numeric stats no longer create huge empty gaps and long string min/max are no longer truncated.

## v0.4.0

### New Features

- **CLI tool (`carquet`)**: Ships a built-in command-line tool for inspecting Parquet files and generating reader code. Built by default (`CARQUET_BUILD_CLI=ON`), installed globally with `make install`.
  - `schema` — print file schema
  - `info` — print detailed file metadata
  - `head` / `tail` — print first/last N rows
  - `count` — print total row count
  - `columns` — list column names (one per line)
  - `stat` — print column statistics
  - `validate` — verify file integrity
  - `sample` — print N random rows
  - `codegen` — generate C reader code from a Parquet file's schema
  - All subcommands support `-h` / `--help`.

- **Code generation (`carquet codegen`)**: Reads a real Parquet file's schema and generates a complete, compilable C program tailored to that schema.
  - `-f` / `--file` — input Parquet file to inspect (generates a placeholder path if omitted)
  - `-o` / `--output` — output source file (prints compile command on stderr)
  - `-b` / `--batch-size` — batch size in generated code
  - `-c` / `--columns` — comma-separated column filter
  - `--mmap` — generate memory-mapped I/O reader
  - `--skeleton` — generate empty `process_batch` body for custom logic
  - Auto-detects compiler (respects `$CC`), carquet include/lib paths, and link dependencies
  - Embeds the source Parquet file as default input so the generated binary works without arguments
  - Generated code compiles with zero warnings

- **Versioned manual in `docs/`**: Added focused in-repo documentation for the main workflows and API concepts.
  - `docs/README.md` — manual index and API surface guide
  - `docs/reading.md` — reader setup, batch scans, column reads, filtering, metadata inspection
  - `docs/writing.md` — schema creation, required/nullable writes, row groups, buffer writer
  - `docs/nested-data.md` — groups, lists, maps, definition levels, repetition levels
  - `docs/performance.md` — mmap, zero-copy, dictionary-preserving reads, prebuffering, tuning
  - `docs/error-handling.md` — status codes, rich error context, type mapping, and level/null conventions

- **Row group predicate pushdown in batch reader**: Added `row_group_filter` callback to `carquet_batch_reader_config_t` for zero-I/O elimination of non-matching row groups using column statistics.
- **I/O coalescing**: Added `carquet_reader_prebuffer()` to pre-read multiple column chunks in a single coalesced read.
- **Speculative footer read**: File open reads up to 64KB from the end in a single I/O call, reducing the open path from 3 I/O calls to 2 for most files.
- **Data Page V2 decoding**: Page reader support for Parquet Data Page V2.
- **Write-path profiling target**: Added the `profile_write` binary for dedicated write-path profiling.

### New APIs

- **Bloom filter query**: Read bloom filters from Parquet files and check value membership — enables column-chunk-level predicate pushdown.
  `carquet_reader_get_bloom_filter()`, `carquet_bloom_filter_check_i32/i64/float/double/bytes()`, `carquet_bloom_filter_size()`, `carquet_bloom_filter_destroy()`
- **Page index read**: Access per-page min/max statistics (column index) and page file locations (offset index) — enables page-level predicate pushdown, skipping individual pages within a column chunk.
  `carquet_reader_get_column_index()`, `carquet_column_index_num_pages()`, `carquet_column_index_get_page_stats()`, `carquet_reader_get_offset_index()`, `carquet_offset_index_get_page_location()`
- **Key-value metadata**: Read and write arbitrary string key-value pairs in the Parquet footer (used by Pandas, Arrow, Spark for schema annotations).
  `carquet_reader_num_metadata()`, `carquet_reader_get_metadata()`, `carquet_reader_find_metadata()`, `carquet_writer_add_metadata()`
- **Column chunk metadata**: Inspect per-column-per-row-group details: codec, encoding, sizes, and which optional features (bloom filter, page index) are present.
  `carquet_reader_column_chunk_metadata()`
- **Per-column writer options**: Override global encoding, compression, statistics, and bloom filter settings on a per-column basis.
  `carquet_writer_set_column_encoding()`, `carquet_writer_set_column_compression()`, `carquet_writer_set_column_statistics()`, `carquet_writer_set_column_bloom_filter()`
- **Buffer writer**: Write Parquet data to an in-memory buffer instead of a file — useful for network protocols, embedding, and testing.
  `carquet_writer_create_buffer()`, `carquet_writer_get_buffer()`

### Performance

- **Multi-row-group pipeline decompression**: Persistent worker pool with pipeline ring buffer for parallel bulk-reads. On 10M-row / 10-RG / 3-column benchmark (Apple M3): snappy 16ms (was 40ms), zstd 25ms (was 44ms), lz4 12ms (was 26ms).
- **ZSTD thread safety**: Per-thread `ZSTD_DCtx`/`ZSTD_CCtx` cache via `pthread_key_create` on all POSIX builds.
- **ARM NEON byte-stream-split**: Widened AArch64 double encode/decode hot loop to 4 doubles at a time.
- **Cheaper page-load peeks**: Zero-length batch reads share the page-loader helper.

### Bug Fixes

- **Fixed BYTE_ARRAY nullable column reads**: Writer now encodes all `num_values` entries for BYTE_ARRAY columns (including zero-length entries for nulls) so values stay aligned with definition levels. Reader's PLAIN decoder and dictionary lookup paths updated to match.
- **Fixed dictionary-encoded nullable columns**: Dictionary index decoding and lookup now process `num_values` entries instead of `non_null_count`.

### Internal

- CLI sources in `src/cli/`: `main.c`, `commands.c`, `codegen.c`, `codegen_read.c`, `codegen_write.c` (stub).
- Build option `CARQUET_BUILD_CLI` (default ON), installs `carquet` binary alongside the library.
- Batch reader pipeline serves pre-read data via zero-copy views from ring buffer slots.
- Worker pool queue capacity increased to 512 for cross-RG bulk-read task submission.
- Page reader fread path uses `prebuf_read_at()` helper for prebuffer cache.
- Windows compatibility: `_getcwd`, `_access`, `_fullpath`, `gmtime_s` behind `#ifdef _WIN32`.
